01The corridor

One trade lane, and everything follows from it

A seller in Bangladesh ships stock to a warehouse in Bangalore. An Indian customer orders. Skydrop phones the customer to confirm — in a cash-on-delivery market an unconfirmed order is a coin flip — then picks, packs, dispatches through Delhivery, tracks the parcel, handles the return when it fails, and pays the seller.

The seller never sets foot in India. That is the product: warehouse, phone call, courier and money movement, so a Bangladeshi merchant can sell into India without Indian operations.

02End to end

Eleven stages

Genuinely a sequence — each stage needs something the one before it produced.

01

Seller onboarding

Invite-only. An admin issues an invitation; the seller registers against that token, sets up profile, encrypted bank details, and the Bangladesh origin address a consignment is booked against. Team members are invited separately with their own role.

Admin → Seller
02

Catalog

Products hang off a shared category tree, variants off products. Categories carry the GST rate and HS code every variant inherits — which is why a seller requests one rather than creating it. Images upload straight to storage through a presigned URL. Bulk import by CSV, with saved column mappings for your own spreadsheet headers.

Seller
03

Inbound consignment

The seller declares what is coming. The warehouse receives it, counts it into bins and batches, and any gap between declared and counted raises a discrepancy. Freight for the BD→India leg is billed here — paid now, or amortised per unit as the stock sells.

Seller → Warehouse
04

Order placement

Manually, by CSV, or through the seller API. The recipient block and per-line SKU details are snapshotted at creation and never re-resolved — editing a product tomorrow cannot rewrite yesterday's order. No stock is reserved yet.

Seller
05

Call confirmation

The order joins a FIFO queue. An agent pulls the next one, phones the customer, records one of nine outcomes. Six count toward the attempt cap; three — callback requested, technical failure, language barrier — do not, because they are not the customer's answer. At the cap the order is rejected, or paused for the seller to decide if they are on manual review.

Call agent
06

Stock reservation

Only on confirmation — a soft quantity claim, no bin or batch yet. Sellers who opt in can hold stock earlier, at placement, with an explicit release decision if the calls run out. Insufficient stock lands the order in OUT_OF_STOCK rather than failing outright.

Automatic
07

Pick and pack

A picker claims the next shipment; the claim expires if abandoned, so work cannot be stuck on someone who went home. Allocation resolves the soft claim to real bins and batches, first-to-expire first out. Short stock escalates to manual placement rather than erroring. Packing resolves races at completion — two packers can pull the same parcel, only one finishes it.

Warehouse
08

Manifest and AWB

Packed parcels auto-attach to a draft manifest, one per courier and warehouse. A supervisor closes it, which requests AWB numbers. One parcel's failure never stops the others — a rejected shipment is retired and replaced, its order routed to manual placement so a human can arrange another carrier.

Warehouse supervisor
09

Dispatch

Handing the manifest to the courier is what decrements physical stock — once, here, and nowhere else in the normal lifecycle.

Warehouse supervisor
10

Tracking, delivery or return

Courier scans arrive as signed webhooks, stored before processing, driving the order forward and never backward. A failed delivery records its reason and can be retried; repeated failure becomes a return, which travels back to be received, inspected, and either restocked or written off. Customers track by AWB on a public page that reveals no internal identifiers.

Automatic · public tracking
11

Money

Delivery accrues the COD amount and debits the shipping charges, but the credit lands after a delay — seven days by default, once the courier has settled. The seller requests a withdrawal; an admin executes it as a remittance. Courier payouts reconcile line-by-line against what each order should have paid.

Automatic → Seller → Finance
03Feature inventory

What each area does

Identity

Staff and seller sessions are separate, each with JWT access tokens and rotating refresh tokens. Re-using a spent refresh token burns the whole family — the standard defence against a stolen session. API keys for machine access. Eight staff roles, six seller-team roles, last-owner protection.

Catalog

Category tree with inherited attributes, GST and HS codes. Products, variants, images with automatic thumbnails. Seller-raised category requests with an admin approve/reject queue. CSV import with reusable column mappings.

Inventory

Multi-bin, multi-batch, FEFO picking. Append-only movement ledger. Two-phase reservations. Goods receipts with discrepancy handling. Cycle counts. Value-threshold adjustment approvals. Low-stock alerts with cooldown. Inter-warehouse transfers that preserve batch lineage.

Per-unit serials

Optional strict mode: every physical unit carries a barcode, scanned at pick, pack, dispatch and return. Set-equality at pack, because a count check passes a swap. The unit ledger is a sidecar — aggregates stay authoritative, and disagreements surface as a report rather than auto-correcting.

Orders

27-status lifecycle behind one transition matrix. Immutable recipient and SKU snapshots. Per-seller customer records with delivery history per address. Manual entry, CSV import, and a seller API. A god-mode override for the cases nothing else covers, with eight guardrails and a permanent mark on the order.

Call centre

Strict FIFO queue with no double-assignment. Nine outcomes mapped centrally to transitions. Attempt caps per seller. Time-based claim expiry. Supervisor queue view with reassignment, plus agent rosters, per-agent metrics and self-service availability.

Warehouse

Pick queue with expiring claims and short-stock escalation. Pack with race resolution at completion. Manifests that find-or-create per courier and warehouse. Dispatch handoff. Full RTO chain: receive at any warehouse, inspect, restock into a lineage-preserving batch or write off.

Courier

Delhivery adapter covering AWB, labels, serviceability, pickups, NDR actions, e-way bills and cancellation. Waybill pooling. Multi-account routing with weighted splits and per-parcel account tracing. Manual placement for anything the integration rejects. Real margin measured against what the courier actually charged.

Tracking

HMAC-authenticated webhook ingestion, stored before processing, with two-layer idempotency. A monotonic-forward guard so a late or duplicate scan cannot move an order backward. Manual scan entry for when a webhook never arrives. Public AWB lookup in English and Hindi.

Money

Append-only wallet ledger in INR and BDT. Delayed accrual after courier settlement. Seller-requested withdrawals, admin-executed remittances. Courier settlement reconciliation with per-order short-payment records. Inbound freight billed per unit by weight. GST invoices as PDFs.

Pricing

Zone and weight-slab rate cards, per-seller discounts and COD fees, surcharge rules, 18% GST applied after surcharges. Full computation context stored with every charge, so a historical price can always be explained. An admin preview that shows its own fallbacks rather than hiding them.

Communications

39 email templates across the whole lifecycle, both seller and customer, English and Hindi. Store-then-send with per-event deduplication, so a retry cannot double-send. Outbound signed webhooks to seller systems, with retry and auto-disable. In-app notifications. Live chat scaffolded.

Support

One ticket system for two populations: damage and scrap raised automatically inside the RTO inspection, and issues raised by sellers. Shared lifecycle, append-only event log, and refunds that credit the wallet inside the same transaction as the resolution.

Configuration

61 settings, typed and admin-editable, 13 of them overridable per seller with server-side clamping. A generic mechanism rather than one column per behaviour — so a seller on different terms is configuration, not code.

Where stock actually moves

Transition Effect Why there
→ CONFIRMED reserve A soft claim on quantity. Late on purpose — an unconfirmed order should not hold stock.
→ DISPATCHED decrement The one physical decrement. Goods have left the building.
→ cancel / reject release Returns the claim. Pre-confirmation cancels release nothing — nothing was held.

Delivery is stock-neutral. The decrement already happened at dispatch. If a future change makes delivery touch stock again, every quantity double-counts — there are tests pinning this specifically, because it was a real bug once.

Margin and float

Margin is what the seller was billed minus what the courier actually charged, read from real invoices rather than a typed-in estimate. It never touches the seller's wallet. Between delivering a parcel and the courier settling, Skydrop is owed money it has not received — every payout is recorded against the orders it covers, so the outstanding float and any short-payment are both countable. A courier underpaying is a dispute with the courier, never a clawback from a seller who was paid in good faith.

Seller teams have six roles — owner, admin, ops, inventory, finance, viewer. Reads are open to all; writes fail closed, so a new endpoint is protected by default and must be deliberately widened.

Role gating in the interface is cosmetic. Hiding a control someone cannot use is courtesy; the server rejects the request regardless of what was shown. When it refuses, the screen shows its exact words rather than guessing at a friendlier version.

08Engineering

Rules that hold it together

Seventeen families of invariant, enforced in code and pinned by tests. The ones worth knowing before changing anything:

  • One writer per thing. Stock moves through a single service; the wallet through a single service; tickets through a single service. Nothing writes those tables directly.
  • Append-only records. Stock movements, tracking events, call attempts, order events and audit logs are never updated or deleted. They are what you read when a number looks wrong.
  • Snapshots. An order keeps its own copy of the recipient and SKU details. Editing the catalog cannot rewrite history.
  • Guard inside the write. Checking a status and then acting on it is not a guard — two people can both pass the check. The condition goes into the write itself.
  • Fail visibly, not silently. Where a sequence cannot be one transaction, the durable step goes first, so a crash leaves a state that announces what happened and can be retried.
  • Refuse rather than guess. A price that cannot be computed is not recorded as ₹0. A webhook that cannot be authenticated is not stored. A URL that cannot be shown to be safe is not fetched.

Security

Three adversarial review rounds. Cross-tenant isolation proven by two real sellers reaching for each other's data. Argon2id password hashing at OWASP parameters, brute-force throttling, injection checked. A per-request nonce content-security-policy on every application. Every stored document — invoices, shipping labels — behind short-lived signed URLs rather than public storage. Credentials encrypted with the key held outside the database, and every decryption audited.

Verification

1,720 automated tests gate every commit: 1,532 unit, 127 integration against a real database, 68 component, and browser tests that exercise the login round trip and the content-security-policy in a real browser. Plus a check that every frontend call resolves to a real API route — the seam where three separate bugs hid, each side passing its own tests while the path between them was wrong.

09Honest list

What is not done

Nothing here is half-built and pretending otherwise.

No write has ever reached Delhivery. The adapter is built against their real API and every read path is exercised, but live writes are switched off and no waybill has ever been fetched. Until one real consignment is booked and cancelled, the write contract is an assumption. The procedure is written and takes about forty minutes.

  • Warehouse setup. The Bangalore warehouse is active but has no bins, and there is no category tree yet. Both are data entry against real shelving and a real catalog.
  • City tiers. 22 cities are priced explicitly; everywhere else falls to zone D until the tier list is decided.
  • GST number. Invoices generate but are not compliant until the GSTIN is set.
  • Live chat. Scaffolded; needs the ChatWoot install.
  • Edge protection. DNS points straight at the origin — no CDN, no web application firewall, no DDoS absorption. Turning the proxy on is a real decision, not a cleanup.
  • Multi-box parcels and reverse-pickup inspection. Both need models that do not exist yet; neither is blocked on anything else.
  • Two commercial calls. What instant credit should cost, and how long an unsold consignment's freight may age before it is called in.
