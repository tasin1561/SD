SEC 01The problem & the wedge

What Skydrop is

Selling into India from Bangladesh fails on six fronts at once — no Indian warehouse, no courier contract, no COD call-confirmation, no warehouse ops, no money rail, no Hindi support. Building all of it solo takes 6+ months, ₹50 lakh+, and an Indian company. Skydrop is the shared backbone that removes every one of those blockers so the seller just sells.

For the seller (BD)

A web dashboard to onboard, manage catalog & inventory, place or bulk-upload orders, watch shipments, and see money owed. No Indian entity required.

For Skydrop staff (IN)

An internal console to approve sellers, confirm orders by phone, pick/pack, dispatch via courier, handle RTOs, and run remittances.

For the end customer (IN)

An ordinary Indian delivery with public parcel tracking. They never see that the seller is across a border.

SEC 02The operational pipeline

How the full system works

One order travels a fully instrumented lifecycle. Every stage is enforced by a state machine — no “any-to-any” jumps — with an append-only event log, and stock is conserved end-to-end (it decrements exactly once, at dispatch).

01 · stock in
Ship & receive
Seller ships inventory once. It lands in a real WMS — bins, batches, FIFO/FEFO.
02 · order
Order placed
Indian customer orders; single entry or CSV. Recipient + SKU snapshotted immutably.
03 · confirm
Call-confirm
Round-robin queue rings the buyer. Unreachable → NDR-routed, never shipped blind.
04 · fulfil
Pick & pack
Bin-level allocation, race-safe pick queue, pack, auto-attach to a courier manifest.
05 · dispatch
AWB & dispatch
Delhivery AWB via API; non-serviceable PINs fall back to manual placement.
06 · track
Track & deliver
Courier scans drive the timeline; public AWB lookup for the buyer.
07 · returns
RTO handling
Returns inspected at the warehouse; restock or write-off, per item, with stock write-back.
08 · money
Remit to BD
COD accrues to a wallet ledger; GST invoicing on our side; remittance back to Bangladesh.
Design discipline that holds it together: a saga pattern (“visible-vs-silent failure ordering”) across every cross-module step, so a crash mid-flow always leaves a self-announcing, recoverable state; three single-source mapping services for call-outcome, tracking-scan, and notification fan-out; and a permanent stock-conservation regression test proving inventory is never inflated or leaked.

SEC 05How it's deployed

Runtime architecture

One application droplet fronts everything; managed Postgres and Spaces are the two external stateful services. The API and workers run in the same Node process today.

Application droplet · SGP1 · 4 GB / 2 vCPU

  • Caddy — TLS + reverse proxy for all subdomains
  • skydrop-api — NestJS + 13 BullMQ workers (in-process) · ~200 MB
  • skydrop-admin :3002 · skydrop-seller :3003 · skydrop-track :3004 — ~125 MB each
  • marketing — static export served from disk by Caddy (no process)
  • Redis 7 — Docker, append-only
  • RAM in use ≈ 1.1 / 3.8 GB · disk 6.7 / 116 GB

External services

  • Managed PostgreSQL 18 — Basic tier, private VPC only
  • Spaces bucket — S3-compatible object store, SGP1
  • Cloudflare — DNS + edge; secrets live in env, never the DB
  • Resend — transactional email

Encryption keys (courier credentials, bank account numbers, webhook HMAC) are AES-256-GCM with the key held in environment variables — never persisted to the database.

SEC 06Load & capacity

How much load it can bear

The current deployment is sized for pre-launch beta, and it is comfortably inside that envelope — the droplet sits at ~29% RAM and near-zero CPU at rest. The honest ceiling is set by two deliberate single-instance choices, not by the droplet.

throughput headroom · single-instance topology
beta · comfortable steady early traffic first bottleneck needs scale-out

Comfortable today

  • On the order of tens of active sellers and hundreds to low-thousands of orders/day
  • A handful of concurrent call-center agents and warehouse staff operating the queues
  • Light JSON reads served in low single-digit milliseconds; the droplet is idle at rest
  • Public tracking is rate-limited per-IP (30/min) and cheap — the highest-volume anonymous surface

What breaks first

  • Postgres Basic tier — caps concurrent connections and write throughput. Order/pick/dispatch flows are multi-statement transactions; this tier is the real ceiling.
  • Single API process — one Node event loop on 2 vCPU. Fine for hundreds of req/s of light work; CPU-bound spikes queue behind it.
  • In-process workers — the 13 BullMQ workers share the API's process, so heavy background bursts compete with request handling.
Scaling path (already designed for): the codebase separates cleanly along these seams — move BullMQ workers into the dedicated apps/workers process; run the API in pm2 cluster mode or across droplets behind a load balancer (rate-limiting already supports a shared Redis store); upgrade managed Postgres and add read replicas; promote Redis to managed. None of these require re-architecture — they are the intended next steps, deferred because beta load doesn't need them yet.
