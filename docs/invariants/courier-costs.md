8. **The nightly cost sync is the only thing that makes margin real, and it fails SILENTLY.** `WalletSyncService` signs in to Delhivery's portal at 02:40 IST (21:10 UTC — the cron carries no timezone, and the page said 21:10 IST for weeks), downloads the wallet export and writes `shipments.actualCourierCostInr` / `actualRtoCostInr`. When it stops, the figures simply stop moving and nobody notices until a margin looks wrong weeks later. It raises an issue when it THROWS; the quieter failures — switched off, or succeeding while matching nothing — had no surface at all until `/cost-sync` (read `courier.accounts.view`, run `courier.accounts.manage`, because a run is a real browser session against a courier login and hammering one is how an account gets locked). **The history is `audit_logs`, not a new table**: every run already writes its whole summary there, and a second copy would eventually disagree (the M14 call, again). **Unmatched rows are normal and are shown as context, never as a warning** — the export covers every parcel on that account and most are not ours; presenting that as an error trains people to ignore the one number that would matter if the matched count ever hit zero. Coverage is TRE-6 made visible: a missing cost is UNCOVERED, never zero, and the forward count EXCLUDES returned parcels because Delhivery refunds the delivery deduction and bills an RTO fee instead.

9. **COST-1 (2026-09-11): a parcel's courier cost is the NET of its wallet transactions, netted from OUR stored ledger — never the latest debit, and never the file.** The import used to keep only the latest successful debit per AWB. On 90 days of real data (23,276 transactions, 11,389 parcels) that was wrong for **705 parcels, ALWAYS overstating — ₹843,191 against a true ₹775,577**. Delhivery charges, reverses and re-charges the same waybill; the reverse-then-recharge pattern happens to leave the latest debit correct, which is exactly why it hid, and a charge followed by a full reversal (net ₹0) was booked at full freight. **`courier_wallet_transactions` is the ledger**: unique on `(courierAccountId, txnId)` — their `MTX…` id, unique in every sheet — so a re-import inserts what is new and touches nothing else. A transaction that comes back with a DIFFERENT amount, direction or waybill is **not applied** — it is counted (`txnsMutated`) and reported, because they correct a charge by adding a reversal, never by editing history. A file carrying the same txn id twice is REFUSED outright. **Net from the TABLE, not the file**: the export is a window, so a parcel debited in June and credited today would net to minus the refund if computed from today's file alone. The shipment columns stay (the P&L and margin report read them) but are now a STAMPED derivation the importer alone writes. **The net is per PARCEL, not per leg.** When a parcel turns round Delhivery refunds the delivery charge and bills one combined return charge, both on rows marked "RTO" — 891 of 921 return-leg credits on the 90-day sample were exactly a forward debit being given back. Netted per leg, 301 parcels read a NEGATIVE return cost. So a parcel with any return-leg transaction carries its whole net on the return column and ₹0 forward; any other parcel carries it forward. **Delhivery `DTO` rows are the return leg** like `RTO` (`legFor()`); read as forward, a received-back parcel's cost sat on the wrong column and the returns line called it uncovered forever. **A parcel whose every stored transaction has vanished from the export is re-netted to NULL** (reported as `costsCleared`) rather than keeping a cost built from rows the courier no longer shows. **A negative net is never stamped** — nobody is paid to carry a parcel, so it means a debit is missing (older than the ledger, or vanished); the old figure stays, the parcel is listed as `incomplete`, and the sync raises a HIGH `MONEY` issue for ours. **A transaction can also VANISH, and mutation detection cannot see that** — it compares a row against itself. On 2026-09-11 four debits dated 7 Sep were in that night's export and absent from a 90-day export covering the same day. Each import therefore judges the span the file actually covers (earliest to latest row): a stored transaction dated inside it and absent from the file is stamped `missingFromExportAt`, KEPT as evidence, and excluded from netting (the later export still balances to the live wallet without it); the stamp clears if it reappears. A vanished or edited transaction raises a HIGH `MONEY` issue per account from `WalletSyncService`, and every cost write records `previousInr`, because before→after is what a dispute with the courier is argued from. **The e2e reset wipes `courier_accounts` by CASCADE** (it references `platform_bank_accounts`), so a spec needing an account creates it in `beforeEach`, after the reset — never in `beforeAll`. **Every courier transaction is recorded at the moment it happened, exactly once — or the import stops.** `occurredAt` is Delhivery's own timestamp read as IST, never the import time. A row marked successful that cannot be read (no id, amount, date or type, or a credit filed under deductions) REFUSES the file instead of being skipped: it used to be counted as "skipped" and the import carried on, dropping real money with only a counter to show for it. Failed/pending rows are still skipped — they are about something that did not happen. Refunds are checked against the file's Summary exactly as deductions are (`LEDGER_REFUNDS_DISAGREE`); only deductions were, so a dropped credit went missing with the totals still "agreeing". **The P&L counts courier adjustments by `occurredAt`, excludes rows stamped `missingFromExportAt`, and cuts days at IST midnight** (`apps/admin/src/lib/ist-day.ts`) — cut at UTC midnight, a charge posted at 02:00 IST on the 1st landed in the previous month, and the line drilldown (which sent a bare date the API read as UTC midnight at the START of the day) silently omitted the closing day while the total above it included it. Verified against production on 2026-09-11: 0 of 23,276 file ids missing, 23,343 rows / 23,343 distinct ids, 181 per-IST-day buckets identical to the paisa, all 37 adjustments identical by id, timestamp, direction and amount.

   **Read `Deductions` and `Refunds`, never the `AWB …` sheets beside them** — those are the same rows minus anything naming no parcel, so reading them silently drops exactly the ledger-level entries (on the sample, a ₹1,290 lost-shipment credit note) and leaves the file unable to reconcile against its own totals. **ADJUSTMENTS are not a parcel's cost even when they carry a waybill** — monthly reconciliations, lost-shipment settlements, fraud credit notes; 36 of the 37 on the sample named an AWB. Identified by their own `stage`/`code` marker in the description, OR by a description naming no waybill (no `wbn`), cross-checked against a free-text shipment status; disagreement resolves to ADJUSTMENT, because a misfiled adjustment is visible on its own line while a misfiled parcel cost silently moves a margin. **AMENDED 2026-09-12 — a Delhivery row that names no waybill is an ADJUSTMENT.** "The two agreed on every row" was wrong for 18: every one of 23,435 real carriage rows carries `wbn` (equal to its AWB), and the 18 stored as parcel without one had a BLANK shipment status, which is in the parcel vocabulary — 12 CREDITS `{"notes":"Claim settled - CMS"}` (₹16,579, 14 Jul – 10 Sep: Delhivery paying out the VALUE of lost goods, which as carriage netted a parcel's cost negative and would have reduced the no-live-parcel line instead of sitting on adjustments) and 6 DEBITS, one lump per "Communication VAS" invoice (`serial_number` naming it, ₹41,705.92). `20260913000000_delhivery_waybill_less_rows_are_adjustments` moved the stored ones (Delhivery accounts only — Shiprocket's passbook never goes through `classify` and has no `wbn`); none named a Skydrop shipment, so no stamped cost moved, and a re-import cannot flip them back (insert-new-only; the mutation check compares amount, direction and waybill, never category). The committed fixture's carriage rows carry `wbn` for the same reason. They are the P&L's **"Courier account adjustments"** line — cost, no revenue, fully measured. **Counted only from `pnl.courier_adjustments_from` (1 Oct 2026, the day every parcel on the accounts goes through Skydrop).** Before it, 12,941 of the accounts' 12,970 waybills were the business's parcels shipped OUTSIDE Skydrop — their cost and revenue are not in the report, so their lost-shipment credits and insurance refunds must not be either; the line's note states how many were left out and their net. Clearing the setting counts everything. **Not a bank entry**: the cash left when the wallet was recharged and that recharge already has one; a deduction consumes prepaid float, exactly as a parcel's carriage does, and a second entry would count the same rupee twice. **The file carries its own integrity proof** — `opening + recharges + refunds − deductions = closing` — reported on every import as `impliedClosingInr`. **An import is always filed under an account**: the manual upload used to pass none, which under netting-from-the-table meant storing nothing and writing costs from a ledger that did not hold the file; it now resolves the default active Delhivery account and REFUSES (`NO_DEFAULT_COURIER_ACCOUNT`) rather than guess. **A dry run nets the stored ledger plus the file's new rows** (and treats what the real run would mark missing the same way) — netting the file alone previewed a return-only file as overwriting the parcel's whole cost.

   **Ninety days a night, via the "Last 90 Days" preset.** Their date picker is a list of named ranges beside a calendar and has NO `input[type="date"]` — the old code looked for two date inputs, found none, returned `rangeApplied: false` every night, and every export came back at the default width while that flag recorded the fact and nobody read it. The window was seven only because the overwriting importer made a wide one expensive; storing by txn id makes the overlap free. A seed edit alone would not have moved the deployed row (create-only), hence `20260911110000_wallet_window_90_days`. **The balance line's "Total Debit" must be read over the SAME window (2026-09-13).** It is compared against the export's sum, and the reconcile kept reading it on the page default after the export moved to ninety days, so production raised HIGH `courier-wallet-totals-disagree:*` nightly (₹1,07,303.22 stated vs ₹12,28,010.68 exported). Both readers now choose the range through ONE helper (`applyLast90DaysPreset`, `pages/wallet-date-range.ts`), both report a `WalletWindow`, and the comparison runs only when the two are the same known window (`sameWalletWindow`). Otherwise it is NOT dropped silently: a MEDIUM `courier-wallet-totals-unchecked:*` names both windows, and an open disagreement is left open. It closes itself once a same-window comparison agrees. **The helper settles the page itself before looking for the picker (14 Sep 2026)**: the ledger download used to click the picker straight after navigating with 5s to find it, so on the night of the 13th it met their loading overlay, exported the page default (seven days) and raised `…-unchecked` while the balance read, which settled first, took ninety. `settleFinancesPage` (network idle, `.ap-loading__overlay` detached) now runs inside `applyLast90DaysPreset`, so neither reader can skip it.

10. **COST-2 (2026-09-11): Shiprocket's wallet is COST-1 too — read off their panel, because their statement API returns nothing.** `ShiprocketWalletSyncService` (portal worker, 03:50 IST, through the NordVPN container — **not** the Bangalore tunnel; see COST-2b) reads the Passbook, Recharge History and Ledger and feeds the Passbook into `WalletImportService.importTransactions` — the SAME store-once / report-mutated-or-vanished / net-from-our-ledger / never-negative path Delhivery's file takes, so the rules are written once. **Their passbook has no transaction id**, so `shiprocket-wallet-rows.ts` derives one: a hash of minute, order, waybill, type, sub category, description and signed amount, plus an ordinal counted from the OLDEST row (three identical pairs in 90 days). The running balance is kept as evidence and deliberately NOT in the key — a recomputed balance would make every held row look vanished. **The passbook proves itself**: each row's balance is the one before plus its amount; that held for all 7,138 rows of the first 90-day read, so ANY break REFUSES the night (nothing stored, HIGH `shiprocket-wallet-chain:*`) rather than netting a ledger with a hole in it. **A recharge is NOT a transaction** ("Bank ReferenceNo: pay_…" under Recharge and Credit) — stored as a credit it would read as the courier refunding ₹10,000 of cost; it goes to `CourierWalletReconcileService.reconcileRecharges` instead. Account-level rows (lost-shipment credit notes, invoice credits, subscription credits, ShipSure premium/refund, charges on orders that never got a waybill) are ADJUSTMENT with no AWB — the P&L's existing adjustments line. **The Ledger is a CHECK, never booked**: its invoices summarise passbook charges and its credits are passbook movements, so booking it would count every rupee twice; each wallet credit it lists must match a passbook movement of the same amount within 15 days (nearest first), and an Early COD credit is not a wallet movement at all. **One writer per cost**: the Shiprocket API sync no longer writes `billing_amount` — it CHECKS it against the ledger's figure and raises `shiprocket-bill-vs-ledger:*` on a disagreement; its write switch was retired by migration (a switch that controls nothing gets flipped and believed). **Netting and matching are scoped by account AND courier**: an Xpressbees waybill routed through Shiprocket has Delhivery's fourteen-digit shape. Their page ignores `current_page` and honours `per_page` only on page one, so the reader picks 100 in their own page-size menu, waits out their loading overlay, and refuses a half-drawn or short page — the first attempt without that read a duplicate ₹460 credit off a page caught mid-render. **A parcel's charges follow Shiprocket's ORDER id, not only its waybill (2026-09-12).** Shiprocket reassigns a parcel a courier will not pick up and issues a NEW waybill under the same order, so its freight is split across two waybills — order 318478638 and six more in the first 90 days (none of them ours, all before the cutover). Nothing on our side rewrites `shipments.awb_number`, so the half under the other waybill matched no shipment and fell to the P&L's "no Skydrop parcel" line, leaving that parcel's cost too low. `courier_wallet_transactions.courier_order_ref` (lifted from `detail.orderId` by migration, Shiprocket only — Delhivery rows carry none) is now matched too: the importer nets every waybill filed under one of our parcels' order ids into that parcel (never a waybill another shipment holds as its own), the "no Skydrop parcel" line does not claim them, and the cost sync's bill check sums freight across both. **The nightly Shiprocket cost sync raises a HIGH `shiprocket-awb-swapped:<shipment>` issue** when their order shows a different waybill from ours — tracking polls by waybill and the printed label carries the old one, so the parcel needs a person; re-pointing it automatically is deliberately not done.


    **COST-2b (2026-09-29): Shiprocket's panel refuses us on TWO signals at once, and either one alone is a wrong diagnosis.** `apiv2.shiprocket.co/v1/auth/login/user` — the SECOND call of their panel's two-step sign-in, and ONLY that path — sits behind an AWS WAF that answers a CloudFront `Request blocked.` with no `access-control-allow-origin` unless **both** the address and the User-Agent are acceptable. Measured five times per cell as a credential-free CORS preflight: NordVPN Mumbai + a `Chrome/…` UA is **200**; NordVPN + `HeadlessChrome/…` is 403; either DigitalOcean address is 403 whatever the UA. The browser therefore reports `net::ERR_FAILED` and their Angular app `status: 0`, which reads as a session that will not hold — so the panel automation failed nightly for a week and was diagnosed wrongly TWICE, once as "it is the IP" and once as "it is the browser, not the address". **Each investigation changed one variable while the other stayed broken.** The fixes are one each: `courier.shiprocket_portal_proxy` is the VPN (`http://127.0.0.1:1082`, egress-check settings SET — `docs/infrastructure.md` §7b), and `desktopChromeUserAgent` / `desktopChromeClientHints` strip the one token that is read, `HeadlessChrome` → `Chrome` (platform and version are not read, so it claims the Linux it really is; **Delhivery's portal is deliberately untouched** — it works, and changing the browser presented to a working site to fix a different one leaves nothing to attribute the result to). **A bare `OPTIONS` is not a preflight and answers 403 from the working exit too**, and so does `curl` with its default UA — that artefact IS the 2026-09-28 conclusion. When measuring an edge refusal, send a real preflight with a browser UA, vary ONE thing, and repeat it: the first run of this one returned 200 and the second 403 because the second had quietly dropped the UA. **A made-up email is the whole test** — Shiprocket answering anything at all proves the request ARRIVED, and no sign-in is spent. The sign-in now asks that question itself: `shiprocketEdgeRefusal` runs one credential-free preflight *before the password is decrypted*, so a blocked address raises `shiprocket-portal-egress:<account>` naming the address instead of burning a login attempt against the account that also handles COD remittance. **The VPN re-picks a server on every restart**, so a future exit may be on the same list; that check is what says so, and `sudo shiprocket-vpn rotate-key` is the remedy.
    **Their invoices are checked against the wallet, nightly (`ShiprocketInvoiceCheckService`, 04:30 IST, after the wallet sync).** The passbook is what we BOOK; the invoice is the tax document for it, and nothing on their side forces the two to agree — on the first 90 days, 91 WhatsApp charges were taken from the wallet and appear on no invoice. Each Freight and VAS invoice's itemized file ("Download Now" in its view — a CSV for freight, a zip of CSVs for monthly VAS, a workbook for ShipSure) is compared with OUR stored ledger, never a second read of their page. Three rules make it quiet when nothing is wrong: **compare per ORDER, never per waybill** (a swapped waybill splits one parcel's freight across two and the invoice bills it under the last — order 318478638 was the one "difference" that wasn't); **judge only what the ledger saw from the start** (a line for a parcel booked before the first stored movement is counted, not flagged — 28 of 29 freight "differences" were exactly that); and **a VAS charge is uninvoiced only once the NEXT monthly invoice has also passed it by** (a month-end charge can land on the following month's). The itemized file must add up to its own invoice, and an unknown service is NAMED rather than matched to nothing. Their invoices settle a discrepancy only if raised within 15 days, so a disagreement inside that window is HIGH (someone is notified) and MEDIUM after it. It changes no cost.

    **COST-3 (2026-09-12): Delhivery's invoices are PROBED before they are checked.** Nobody had seen where Delhivery keeps invoices or what their itemized files look like, so a one-off, operator-triggered, READ-ONLY probe comes first: `POST /admin/courier-portal/delhivery-billing-probe` (`courier.accounts.manage`, audited before the enqueue) queues `probe-delhivery-billing` on the wallet sync's OWN queue, whose worker runs one job at a time, so it can never share the Delhivery login with the 02:40 sync. It signs in through `PortalSessionService` (never a second credential path), discovers the billing area, reads the invoice list and describes the latest invoice's files (caps: 14 pages, 8 downloads, 10 minutes, no retry). Findings go to one `audit_logs` row (`courier.delhivery_billing.probed`) with session material scrubbed; raw files and screenshots go to `courier-probes/delhivery-billing/<runId>/`; `GET` pairs the request with its result and presigns the files. **Every click goes through `judgeClick`, which reads the element's OWN label and refuses pay / dispute / raise / submit / delete / cancel / update / save and their relatives, any unlabelled control, and any form submit** — a refused download is a missing file the report names; a permitted write cannot be taken back. Like the wallet sync it ignores `portalMode` (CUR-18 stops the escalation automation, not an operator's read) but stops on an open sign-in challenge. The Delhivery invoice check is to be written against what this finds, never against guesses. **AMENDED 2026-09-12, after the first run (73487b0b):** the invoices are at `/finances/invoices/invoice_list` (tabs Invoice List / Credit Notes / Debit Notes) and the probe goes there FIRST, discovery being the fallback. **A list is not read until it has drawn** — every navigation, range change, tab or page change first draws twenty grey placeholder rows, and the first run read them as data (20 empty rows, nothing downloaded); `waitForRows` looks again for up to 20s until a row carries an id, an all-empty row is loading, and a lone "no data" row is empty. If "Last 90 days" never draws, the default range is read and `range.fellBack` says so. Each row's control is a "Download ⌄" MENU: for the latest invoice of each service type and the latest credit and debit note it is opened, every option recorded (`downloadMenus`), and each option naming a file clicked through `judgeClick` for its download (`files`).     **A courier's EARLY-COD FEE is a cost the wallet never sees (2026-09-11).** Shiprocket takes it out of the COD payout and invoices it separately ("COD Remittance Fee" — ₹120 / ₹440 / ₹90 in May–July), so neither the wallet sync nor the parcel costs can see it, and recording the payout used to leave it as a capital "shortfall" no report counted. A payout now records what the courier KEPT BACK by kind (`courier_settlements.early_cod_fee_inr` / `freight_deducted_inr` / `rto_reversal_inr`, filled from their remittance file's CRF sheet), and `amount + kept back = allocated` is what "fully explained" means (MEDIUM, not HIGH). **The fee is GROSSED UP**: the bank takes the full COD in and posts the fee out as an `EXPENSE` entry, category `courier_cod_fees`, linked by `settlementId` — netting to exactly the statement, visible on /expenses, and counted by the P&L's **"Courier COD fees"** line. **Operating expenses exclude settlement-linked entries**, or the fee comes off gross and net (the same rule as a freight bill's linked payment). **Freight kept back is Shiprocket POSTPAID — a wallet TOP-UP, never a cost.** Their docs: "a part of it goes to your Shiprocket wallet while the remaining amount is transferred to your bank account"; the freight is then debited from the wallet like any other, so it is already each parcel's cost. The payout grosses it up and posts it out as a `COURIER_WALLET_RECHARGE` (reference `COD-<utr>`) with an already-MATCHED `courier_wallet_recharges` row (or the paid-but-never-arrived check calls it money lost); the passbook's matching credit is set aside as a `codTopUp` (recognised by COD / CRF / remittance / postpaid wording) instead of being stored as the courier's credit — which would read our own money as income; and the wallet sync pairs the two (same amount, within 15 days) and raises `shiprocket-cod-topup-unseen:*` / `shiprocket-cod-topup-unrecorded:*` when either half is missing. That pairing is the safety net for wording we have not seen yet: none of it has appeared in the first 90 days. An RTO reversal kept back stays against capital, named, until the clawback lands. Do not file these fees by hand on /expenses.
