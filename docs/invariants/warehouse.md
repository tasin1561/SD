**Warehouse Operations rules (Module 8 — WMS-1 through WMS-9, NON-NEGOTIABLE):**

1. **WMS-1: Pick-queue semantics. AMENDED 2026-09-03 — picking is PRINT-FIRST and batched.** The everyday path is `/warehouse/printing`: select parcels → print labels → confirm → select labelled parcels → print ONE consolidated sheet → confirm → walk → mark picked. `CONFIRMED → PENDING_PICK` now fires when the PICKING SHEET IS CONFIRMED PRINTED (`PickBatchService.confirmPrinted`), and `PENDING_PICK → PICKED` when the picker returns (`PickBatchService.markPicked`). **Confirming the print is what ALLOCATES phase-2** — that is what makes the bin codes on the paper real rather than a guess, and it means a shortfall surfaces at the desk before anybody walks. The per-parcel station (`PickExecutionService.start/recordItem/complete`) is RETIRED from the nav but NOT deleted, and must not be: in STRICT mode the scan at pick is what binds units to a parcel and pack demands the scanned set equal exactly those (UNIT-2), so `markPicked` REFUSES a serialised parcel by name rather than closing it from paper. It is also the escape hatch for a one-off parcel. **`PickExecutionService.complete` and `PickBatchService.markPicked` are the only two writers of `OrderStatus.PICKED`; the pack queue selects on exactly that, so anything that retires one without providing the other strands every parcel mid-floor.** The original text follows, still true of the per-parcel path: the `CONFIRMED → PENDING_PICK` transition fires on the picker's FIRST START (`PickExecutionService.start`), not on `pullNext`. Pick expiry (WMS-5) leaves the order in `PENDING_PICK` and only clears `shipments.pickStartedAt`, re-pickable via the `pickStartedAt IS NULL` filter — no `PENDING_PICK → CONFIRMED` bounce. WMS-4's `PENDING_PICK → PENDING_MANUAL_PLACEMENT` is the shortfall escalation (no side-effects; M5 conservation keeps residual phase-1).

2. **WMS-2: `pullNext` concurrency.** `PickQueueService.pullNext` and `PackQueueService.pullNext` both use `FOR UPDATE OF s SKIP LOCKED LIMIT 1` inside the locking tx — `OF s` restricts the row lock to `shipments` ONLY, so the joined `orders` row stays read-only and a concurrent `OrderWriteService.transitionStatus` (which locks the order row) can never deadlock against a pull. Eligibility is the AUTHORITATIVE order status joined into the locking SELECT (WMS-1/WMS-9): pick = `s.status='created' AND s.pick_started_at IS NULL AND o.status IN ('confirmed','pending_pick')`; pack = `s.status='created' AND s.pack_completed_at IS NULL AND o.status='picked'`. The order-status predicate is a HARD filter, not a proxy — `ShipmentProvisionService.voidForOrder` is best-effort, so a lagged void must still be excluded here.

3. **WMS-3: Pick-allocation outer retry over M5.** `PickAllocationService.allocateForPick` wraps `StockPickAllocationService.allocateAndPopulate` with an OUTER retry/backoff (`ops.pick_allocation_retry_max` seeded 3, `ops.pick_allocation_retry_backoff_ms` seeded `[100,250,500]`). M5's own version-CAS inner retry (INV-6) handles transient conflicts; this layer turns the rare *terminal* `PICK_ALLOCATION_CONFLICT` into a non-terminal `PICK_ALLOCATION_RETRY_EXHAUSTED` so commit-6 can fail-route to PENDING_MANUAL_PLACEMENT rather than 500. Only the typed 409 is retryable; `NotFound` / `RESERVATION_NOT_ACTIVE` / `strategy: 'NONE'` (stock not arrived) pass through.

4. **WMS-4: Pick shortfall fail-routing.** When `PickExecutionService.start` cannot fully allocate (any reservation returns shortfall / strategy NONE/PARTIAL / RETRY_EXHAUSTED, or the order has zero ACTIVE reservations — a data anomaly), the saga transitions `PENDING_PICK → PENDING_MANUAL_PLACEMENT` (the commit-1 matrix edge, empty side-effects). M5 conservation keeps the residual phase-1 reservation; supervisor resolves. NEVER 500.

5. **WMS-5: Pick-task expiration.** Time-based idempotent CAS (mirrors CC-7). A delayed BullMQ job carries the `pickStartedAt` it was scheduled for; a guarded `updateMany` on `(id, status=CREATED, pickStartedAt=<that exact value>, pickCompletedAt IS NULL)` reverts the claim (clears `pickStartedAt`/`pickStartedByStaffId`/`pickExpiresAt`). Vanished / completed / re-pulled / lost-the-race all no-op, so BullMQ retries, duplicate deliveries, and an old timer racing a fresh re-pull can never double-expire. POST-CAS it calls `StockPickAllocationService.releaseAllocation` per ACTIVE reservation (collapses the phase-2 split back to a single conserved phase-1 row, INV-4) — best-effort, idempotent; failure swallowed (next pull's `allocateAndPopulate` tolerates residual phase-2 idempotently). `expire()` is public — doubles as the supervisor manual trigger. Custom BullMQ jobId must be colon-free (epoch-ms encoding).

6. **WMS-6: Manifest close = supervisor saga + M9 AWB stub.** `ManifestService.close` is `WAREHOUSE_SUPERVISOR`/`SUPER_ADMIN` only (controller-gated via `requireStaffRoles`). The CLOSURE TX (manifest `updateMany` guarded on `(id, status=DRAFT)` → CLOSED + closedAt + closedByStaffId + audit MEDIUM) commits atomically; POST-COMMIT per-shipment `PACKED → PENDING_DISPATCH` transitions are each their own `transitionStatus` tx (matrix edge has empty side-effects, verified) — failures collected into `result.failures` and the loop continues (manifest correctly CLOSED is the supervisor's intent; failures surface for investigation, do NOT undo closure). The Module-9 AWB enqueue is a STUB: audit HIGH `manifest.awb_enqueue_stub` with `metadata.{manifestId, shipmentIds, transitionedCount, failureCount, moduleStubbed:'M9'}`. `ManifestStatus` is intentionally `DRAFT`/`CLOSED` only for M8; M9 extends with `AWB_PENDING`/`CONFIRMED`/`FAILED`. Idempotent on already-CLOSED.

7. **WMS-7: Manifest find-or-create + move (DRAFT↔DRAFT).** `PackService.complete` auto-attaches the packed shipment to a DRAFT manifest via `ManifestService.attachShipment` (POST-COMMIT, best-effort, idempotent) — find-or-create one DRAFT per `(courierCode, originWarehouseId)`. Concurrency: per-pair `pg_advisory_xact_lock` (namespace `0x04d47`, JS FNV-1a 32-bit key on `<courier>|<warehouse>`) serializes concurrent attaches for the same pair so parallel DRAFTs never appear; distinct pairs uncontended. Numbering format `MF-YYYY-MM-XXXXXX` (mirrors `ShipmentNumberingService` per-year sequence + advisory lock 0x04d46 'MF'). `ManifestService.moveShipment` reassigns a packed shipment from one DRAFT to another (both DRAFT, same courier + warehouse — `SOURCE_MANIFEST_CLOSED` / `TARGET_MANIFEST_NOT_DRAFT` / `COURIER_MISMATCH` / `WAREHOUSE_MISMATCH` guards). Phase-1A: single courier → single DRAFT typically → moveShipment is dormant; reachable when M9 multi-courier lands.

8. **WMS-8: RTO finalize = movements-first two-gate saga.** This paragraph described an interim "release-based" (Model B) design that never shipped to production — Module 9 (bug-1 fix) and Model C (2026-09-03) both landed before it did; see CUR-3 for the currently-accurate model. `RtoDispositionService.finalize` is: **RESTOCK** = `mutation.apply(tx, RETURN_RESTOCK, +qty)` per line — the unit physically left the building (at pack, under Model C) and has now come back — **no** reservation release (already FULFILLED, long before RTO_RECEIVED is reachable). **WRITE_OFF** = `mutation.apply(tx, ADJUSTMENT_DECREASE, -qty, reasonCode: <mapped from rtoCondition>)` (DAMAGED→DAMAGED_IN_WAREHOUSE, MISSING→LOST, GOOD/null→OTHER — debt entry tracks a dedicated RTO_* value). Order goes to `RTO_RESTOCKED` regardless of restock/write-off mix. **Two-gate idempotency:** Gate 1 = `order.status===RTO_RESTOCKED → alreadyFinalized`; Gate 2 = `stockMovement.findFirst({shipmentId, type:RETURN_RESTOCK or ADJUSTMENT_DECREASE})` skips re-apply (`stock_movements` has no native dedup key — the explicit existence query IS the gate). **Saga ordering: movements first, transition last** — visible-vs-silent failure ordering (see "Saga: visible-vs-silent failure ordering" below). The original commit-15 design INFLATED stock in one direction and a later interim design leaked reservations in the other — both caught by the full-lifecycle conservation e2e, which remains as a permanent regression guard and needed NO changes for Model C (finalize is decoupled from which matrix edge fired the original decrement — see CUR-3).

   **WMS-8c (2026-09-13): a RESTOCK goes back to where PACK_CONFIRM says the unit LEFT.** The RETURN_RESTOCK target used to be `shipment_items.pickedBinId/pickedBatchId` alone — a hint only the retired per-parcel station wrote — so every batch-picked return was refused (`RTO_RESTOCK_MISSING_CONTEXT`; 6 of 13 real lines on production). Finalize now resolves each RESTOCK line from the order's PACK_CONFIRM movements (DISPATCH for pre-Model-C orders), **queried by orderId** (a supersede leaves them on the original shipment, CUR-3), net of PACK_REVERSED (per movement, `metadata.reversesMovementId`), grouped by (warehouse, bin, batch): a line that left from two places restocks the same split, one RETURN_RESTOCK per source through `RtoRestockTargetService` exactly as before (R6b). **The movement beats the hint** — it is where `qtyOnHand` was actually decremented; a disagreeing hint is audited (`hintDisagreements`), never refused. The hint is used only when a line has no pack evidence at all (`restockedFromHintOnly`). **A line with neither never left stock through us and is refused by name** (`RTO_RESTOCK_NEVER_LEFT_STOCK` — "choose Write off"); more units than left is `RTO_RESTOCK_EXCEEDS_STOCK_LEFT`, never a partial restock. `PickBatchService.markPicked` now stamps the hint from the phase-2 reservation `buildList` allocated (largest per line, guarded on both columns NULL, best-effort); `20260913010000_backfill_pick_hints_from_pack_movements` filled existing single-source lines. The pure resolver is `warehouse-rto/services/rto-restock-sources.ts`.

   **WMS-8d (2026-09-13): a returned line is inspected BY QUANTITY, and "Keep aside (damaged)" is a fourth disposition.** Owner: "what if this product has 2 qty? one is good and another is damaged?" — condition and disposition lived once per `shipment_items` row, so both units got one choice. **`shipment_item_rto_inspections` holds the truth per unit** (`quantity`, `condition`, `disposition`, `notes`, `position`; FK shipment_items CASCADE; UNIQUE `(shipment_item_id, position)`), written ONLY by `RtoInspectionService`, which replaces a line's rows wholesale AFTER updating the `shipment_items` row (that update takes the row lock, so two inspectors on one line serialise instead of interleaving rows). The request is ONE verdict (`condition` + `disposition`, still the default — one row covering the line) or `rows`, never both (`RTO_INSPECTION_AMBIGUOUS`); rows must cover the line's quantity exactly (`RTO_SPLIT_QUANTITY_MISMATCH`), each ≥1 unit. **`shipment_items.rto*` are now a SUMMARY** (`summarizeRows`): worst condition (MISSING > DAMAGED > GOOD); disposition by INSPECT_LATER > RESTOCK > HOLD_DAMAGED > WRITE_OFF, so "undecided" and "something restocks" still read correctly off the line; distinct notes joined. Readers needing units read the rows via `effectiveRows`, which also turns a line inspected before rows existed into one row — exactly what `20260913020100_rto_inspection_rows` backfilled for every inspected line (no inspection lost). **A line with serialised units is NOT split** (`RTO_SPLIT_SERIALIZED_LINE`) — a row does not say which serial went which way, so STRICT lines keep one verdict and the unit ledger stays exact. **Finalize applies per row**: the line's RETURNING quantity (RESTOCK + HOLD_DAMAGED) is resolved once against the pack sources (WMS-8c), so `RTO_RESTOCK_NEVER_LEFT_STOCK` / `RTO_RESTOCK_EXCEEDS_STOCK_LEFT` guard all rows of the line together, and `splitSourcesAcrossRows` hands the sources to the rows in row order (deterministic; a source straddling two rows is cut). RESTOCK → RETURN_RESTOCK into the returns hold (BIN-3) as before; **HOLD_DAMAGED → RETURN_RESTOCK into the RECEIVING warehouse's DAMAGED bin** (`RtoRestockTargetService.resolveDamagedHold` — source batch same-warehouse, R6b child batch cross-warehouse), never sellable because DAMAGED is in `NON_PICKABLE_BIN_TYPES` (BIN-2), and refused with `RTO_NO_DAMAGED_BIN` when the warehouse has none — never a silent fallback (hold would let putaway shelve it, storage would sell it); WRITE_OFF → no movement, and **its inbound-freight share is charged for the written-off UNITS only** (`debitForWrittenOffItems` takes `{shipmentItemId, quantity}` lines); a kept-aside unit owes no freight (it has not left). INSPECT_LATER on any row blocks. Every RETURN_RESTOCK of a finalize is written in ONE tx, so gate 2 is unchanged. **Order status: any RESTOCKED unit ⇒ RTO_RESTOCKED, otherwise RTO_DAMAGED** (kept-aside counts as not restocked). The unit ledger moves only for an unsplit line (a kept-aside unit goes IN_STOCK at the DAMAGED bin, gate `RTO_HOLD_DAMAGED`). **Putaway offers RESTOCKED units only, out of RTO_HOLD only** — it used to search every non-pickable bin, which would have offered the DAMAGED bin to a shelf. The scrap ticket is still ONE per line and says it unit-group by unit-group ("1 of 2 arrived damaged: we are keeping it aside for you… · 1 of 2 is in good condition: we are putting it back into your sellable stock"); a changed split on an open ticket adds our note. **A kept-aside unit leaves later by an Inventory → Adjustments DECREASE from the Damaged bin** with `RETURNED_TO_SELLER` (now offered by the admin form — the API always accepted it) or `DAMAGED_IN_WAREHOUSE`. Pure logic: `warehouse-rto/services/rto-inspection-rows.ts`.

   **WMS-8e (2026-09-14): a return is BOOKED into the returns hold at RECEIVE and MOVED out of it at FINALIZE.** Owner: "R-01-01 should hold products that are received but not decided yet or will decide later. Then Put back in stock goes to floor. D-01-01 (damaged) for damaged." Before this nothing moved at receive, RESTOCK landed in RTO_HOLD at finalize and a putaway made it sellable, so a received-but-undecided return was on no ledger. **Receive** (`RtoReceiptService`) — after the stamp, BEFORE the transition, and only in the call that WON the stamp — books each line's units that LEFT through us (the WMS-8c pack evidence with `allowPartial`: less evidence than the line books what left; a pick hint alone, or nothing, books nothing — the seeded SH-TEST parcels) into the receiving warehouse's RTO_HOLD bin as `RETURN_RECEIVE` +qty (an enum value that existed and nothing wrote), one per (bin, batch) left from, in that batch or its R6b child batch cross-warehouse, `metadata.shipmentItemId` + `leftFrom*`, all in ONE tx. Gates: the stamp win (two concurrent receives cannot both book) plus an existence query for a prior `RETURN_RECEIVE` on the shipment; the already-received short-circuit never books (a finalize may already be reading RTO_RECEIVED). **The booking never blocks the receive** — the response's `holdBooking.outcome` is BOOKED / NOTHING_TO_BOOK / NO_HOLD_BIN / FAILED / SKIPPED. **No RTO_HOLD bin**: the receive is recorded, nothing is booked, and a MEDIUM `OTHER` issue `rto-hold-bin-missing:<warehouseId>` says so (bumped per parcel, cleared by the next booking there) — refusing would leave a carton on the bench with no row behind it, and nothing is lost because the parcel then finalizes the unbooked way below, which conserves stock on its own; the receive toast says it too. A thrown booking is logged and degrades the same way. STRICT units of a booked line go IN_STOCK at the hold bin (the discrepancy report counts IN_STOCK against qtyOnHand); others stay RTO_RECEIVED. **Finalize asks the ledger, per LINE, whether receive booked it** (its `RETURN_RECEIVE` — never a date). A booked line's held units are handed to its rows (`splitHeldAcrossRows`: returning rows first and in full, write-off rows from what is left) and leave the hold through `StockMutationService`: **RESTOCK** = a paired TRANSFER_OUT / TRANSFER_IN (one `transferGroupId`, same batch) to `RtoRestockTargetService.sellableDestination` — the FLOOR bin when bin tracking is off (`BinPolicyService`), else the shelf the unit left from / was picked from when it is in this warehouse and still pickable (`findUsableShelf`, the ONE test, shared with putaway's suggestion), else FLOOR — sellable at once; **HOLD_DAMAGED** = the same pair to the DAMAGED bin (`RTO_NO_DAMAGED_BIN` if none, the tx rolls back and the units stay in hold); **WRITE_OFF** = `ADJUSTMENT_DECREASE` out of the hold, reasonCode DAMAGED → DAMAGED_IN_WAREHOUSE, MISSING → LOST, GOOD → OTHER (INV-7; `writeOffReasonCode`), its inbound-freight share charged exactly as before (one INBOUND_FREIGHT entry per order); INSPECT_LATER still blocks and the units stay in hold. More returning than booked is `RTO_RESTOCK_EXCEEDS_STOCK_LEFT`. **An UNBOOKED line** (received before WMS-8e — production's SD-2026-26-000009 and SH-TEST-523902 — or where there was no hold bin) finalizes exactly as WMS-8c/8d say, except that RESTOCK's RETURN_RESTOCK now lands in the same sellable destination instead of the hold (RTO_RESTOCK_NO_TARGET_BIN is gone: FLOOR self-heals). **Gate 2** is an existence query for ANY finalize type on the shipment (`FINALIZE_MOVEMENT_TYPES`: RETURN_RESTOCK / TRANSFER_OUT / ADJUSTMENT_DECREASE — nothing else writes those with a shipment id), and every movement of one finalize, booked and unbooked lines together, is ONE tx. **Putaway survives only for units a pre-WMS-8e finalize restocked INTO a hold bin** (a RETURN_RESTOCK into RTO_HOLD for that shipment — nothing written since produces one), and it subtracts the undecided units booked into the same hold row (their RETURN_RECEIVE net of the finalize moves out, both carrying a shipment id) so it never offers a return still waiting for its decision. No backfill and no migration writes stock (INV-1). Pure logic: `warehouse-rto/services/rto-held-returns.ts`; ledger reads: `rto-stock-evidence.ts`.

9. **WMS-9: Order status is the authoritative lifecycle gate.** `shipments.pickStartedAt/pickStartedByStaffId/pickExpiresAt/pickCompletedAt/packCompletedAt/packedByStaffId` + `shipment_items.rto*` + `shipment_items.pickedBinId/pickedBatchId` are all OPERATIONAL who/when columns + hints — NOT cross-domain authority. The authoritative pick-allocation source-of-truth is the phase-2 `stock_reservations` (INV-4); the authoritative pick context is the order's lifecycle status. `complete` validates fully-allocated via the order-status gate (a shortfall already escalated at start, so reaching `complete` in PENDING_PICK ⇒ allocation succeeded) + "every shipment_item recorded" — NOT against the hint columns. Cross-module readers never query `shipments.*` operational columns to make decisions; they go through `OrderReadService` / `OrderWriteService.transitionStatus` (ORD-3 / MUST #16).

**Module 8 architecture (R3 + facade):**
- The shipment-provision PRIMITIVE lives in a standalone `shipment-provision` module (`ShipmentProvisionService.provisionFromSnapshot` / `voidForOrder`, `ShipmentNumberingService`; NO Order dependency). Imported by `order` (commit 16 CC-6 dual-path) AND the warehouse modules; it imports neither. The fourth successful **R3 split** after M4/M5/M7. **R3 snapshot-DTO refinement:** shared primitives are DEPENDENCY-FREE — if the operation needs upstream data, the CALLER marshals it as a DTO rather than the primitive resolving via service calls. M7's `call-queue` takes `orderId` (the queue is keyed on it; the primitive needs no Order data); M8's `shipment-provision` takes a full `ProvisionShipmentInput` DTO (shipment construction needs the recipient block + item snapshot, which the caller builds from the order it already loaded — `OrderWriteService.transitionStatus` does exactly this on entry to CONFIRMED, leveraging the snapshot already inlined in its order load).
- Module split: `warehouse-pick` (Picker/AdminPick controllers + PickQueueService.pullNext + PickAllocationService + PickExecutionService.{start,recordItem,complete} + PickExpiration{Service,Queue,Worker}); `warehouse-pack` (PackerController + PackQueueService.pullNext + PackService.complete with WMS-7 post-commit auto-attach); `warehouse-manifest` (AdminManifestController + ManifestService.{attachShipment, moveShipment, close, listManifests, getById} + ManifestNumberingService); `warehouse-rto` (WarehouseRtoController + RtoReceiptService + RtoInspectionService + RtoDispositionService). All four are LEAF consumers — nothing imports them.
- Cross-module export surface: `ShipmentProvisionService` (from `shipment-provision`) only — the R3 primitive `order` and warehouse-* call into. The warehouse modules export NOTHING externally.
- Pack queue model (locked decision): VIRTUAL FIFO query, no `pack_queue_entries` table — entry to `PICKED` makes the shipment eligible by construction via the pullNext filter. The "enqueue on PICKED" hook in `OrderWriteService.transitionStatus` is an INLINE post-commit audit (`pack_queue.eligible`, LOW) — the observability extension point for future BullMQ/WebSocket packer-notification (then replace with the real enqueue; mirrors the CC-6 enqueueForCall shape).
- **Pack claim model — SUPERSEDED by the pack BOX (2026-08-01).** The original decision was NO persistent claim: `pullNext` informational, race resolved at `complete`. That is wrong once ten packers work in parallel — two can fill the same physical box and only collide when one saves. **PACK-1: the box is the claim, and it is taken UP FRONT.** A packer scans the shipping label to open a `pack_boxes` row, scans each product in, scans the label again to close (which still runs `PackService.complete` — the stamp, the PICKED→PACKED transition and the WMS-7 manifest attach all stay where they were). Exclusivity is TWO PARTIAL UNIQUE INDEXES — `one open box per shipment` and `one open box per packer` (the "panel is locked until the box is closed" rule) — never an application check: a read-then-write guard under READ COMMITTED lets two concurrent packers both read "no open box" and both proceed. **These need an INTEGRATION test to mean anything — a mocked Prisma has no index to violate** (same lesson as the `courier_pickup_requests` partial unique). Contents are verified as a SET at close, per SKU and per unit; a count alone passes a box with two of one item and none of another. Over-scanning is refused AT THE SCAN, not at close. **PACK-2: cancelling a box returns NOTHING to inventory.** This predates PackService.complete's own decrement (Model C, 2026-09-03) — by the time a box exists to cancel, `PICKED → PACKED` has NOT yet fired (the box is opened before the label is scanned to close it, and `complete` is what carries `DISPATCH_STOCK`), so there is still nothing to give back at cancel time: stock leaves exactly once, at the CLOSING scan (CUR-3) — re-adding here would inflate on-hand by the size of the box, the same class of error as the pre-fix RTO path. Cancel discards the scans, returns serialized units to PICKED and re-queues the parcel; `pack-box-flow.e2e-spec.ts` asserts on-hand and reserved are byte-identical across a cancel, so a future "fix" fails. An abandoned box is reclaimed by a FIVE-MINUTE sweep (`ops.pack_box_timeout_minutes`, 60) — faster than the hourly sweeps because this one blocks a parcel AND its packer.
