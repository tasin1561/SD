**Product labelling rules (LBL-1 through LBL-3, 2026-09-04 — NON-NEGOTIABLE).**

1. **LBL-1: EVERY product carries a scannable label, in BOTH inventory modes.** The pack bench verifies a box by scanning what goes into it and resolves a scan to a serial (STRICT) or a SKU-level code (NORMAL) — and until now nothing PRINTED the second one. Production had 5 variants, **0 with a barcode**, all NORMAL, 0 stock units, 0 pack boxes: the contents check was structurally unable to run, and the 7 parcels that shipped went through `PackService.complete`, which stamps the pack without verifying anything. `SkuLabelService` prints one sticker per unit RECEIVED (not per unit expected — labelling what was ordered leaves spares in a drawer, and a spare sticker is a duplicate waiting to be stuck on the wrong thing), from the goods receipt, because receiving is when the goods are in front of somebody and the counts are known. STRICT units additionally carry their own serial from the consignment sheet; a NORMAL scan proves "the right product", a STRICT scan proves "the right ONE". **AMENDED 2026-09-15 (owner): barcodes follow each product's inventory MODE.** A STRICT product carries ONLY its own unit serials — printed once from the consignment (LBL-5), a damaged one replaced per unit — and never a reusable SKU sticker: `SkuLabelService.forGoodsReceipt` leaves strict lines out and names them (`skippedStrict`, also in the `warehouse.sku_labels.built` audit row), and `forVariants` (Warehouse → Printing → Find a product) refuses one with `STRICT_PRODUCT_USES_SERIALS`. A NORMAL product has one barcode per SKU, reprinted freely under `warehouse.pick`. **The picking list decides the barcode PER LINE** (`PickListLine.strict`; `strictMode` means "any line strict"): a normal line prints its SKU barcode, a strict line prints "STRICT — scan each unit" in the cell. It was per SHEET — one strict product blanked every barcode on the walk. Every sticker sheet built is recorded (`warehouse.sku_labels.built`, LOW: who, source, SKUs × quantity) and listed under "Recently printed stickers" on Find a product; it records a sheet BUILT, not paper printed.

2. **LBL-2: the scannable code is `variant.barcode ?? skuCode`, and NOTHING is minted or persisted.** Generating an `SDS-XXXX` and saving it to `product_variants.barcode` was the obvious first design and carries a trap: the day the seller fills in their real EAN, every sticker already on a shelf silently stops resolving. The SKU code is a value the seller already owns and is unique per seller, and `PackBoxService.scan` accepts **both** (`OR: [{barcode}, {skuCode}]`), so a label printed today survives the seller adding a barcode later. That lookup is **scoped to the order's seller** — `barcode` has no uniqueness constraint and `skuCode` is unique only per seller, so an unscoped lookup can resolve another seller's product; it failed closed before, but on the wrong reason ("not on this order" when the truth is "that is somebody else's SKU").

3. **LBL-3: Code 128 is encoded ONCE, on the server, and the client only draws.** `common/barcode/code128.ts` (moved out of `warehouse-printing` when a second module needed it) is the single encoder; `printableBarcode()` returns module widths, and `<Barcode128>` in `@skydrop/ui` renders rects from them. **Never add a client-side encoder or a barcode library**: a second implementation that disagreed would not fail loudly — it would print a symbol that scans as a DIFFERENT value than the text beside it, and the label would agree with itself all the way to the wrong customer. An unencodable value yields `widths: null` and prints as text, rather than failing the whole sheet — one bad SKU must not cost the warehouse its other forty labels. Serials were a monospace string until 2026-09-04 (a deliberate stopping point at the time); that made STRICT mode a typing exercise at every gate, which is both slow and exactly where a transcription error puts the wrong unit on an order.

**LBL-5 (2026-09-04): a unique serial is printed ONCE; a reprint is per unit, permissioned and recorded.** A SKU label is *meant* to be identical on every unit, so reprinting it is free. A STRICT serial names ONE physical item, so a second copy is how two boxes come to claim the same unit — and `stock_units` is `@@unique(sellerId, serialBarcode)`, so the ledger cannot even represent the duplicate: one of the two silently becomes a ghost, and it surfaces later as a unit already picked for a different parcel, at the bench, with a customer waiting. `ConsignmentLabelService.print` now REFUSES a second sheet (`LABELS_ALREADY_PRINTED`, naming when it was labelled) — the guarded `updateMany` only ever stopped the STAMP moving (which is what locks the station, CNS-5); the sheet itself came back every time, so reprinting was unlimited and only the first was recorded. The escape hatch is `reprintUnits`: NAMED serials only (capped at 25 — "a reprint of four hundred" is a whole-sheet reprint wearing a hat), behind its own `warehouse.labels.reprint` permission rather than the one that prints the sheet, reason ≥20 chars, audited HIGH, and appended to **each unit's own ledger** as a `LABEL_REPRINT` event via `StockUnitService.recordLabelReprint` (UNIT-1 — the label service cannot write `stock_unit_events` itself) because the question asked later is "has THIS serial been printed twice?", which is a question about the unit and not about the sheet. **The serial is reprinted AS-IS, never reissued**: a lost label may yet turn up on the same box, and minting a new serial would make the original — still stuck to the unit — scan as something that does not exist. A serial not on the consignment is NAMED rather than dropped; printing four of five with no comment is how the fifth box stays unlabelled. **AMENDED 2026-09-15 (owner): a reprint takes TWO people — request, then approve.** The one-step `reprintUnits` and its route are GONE; `LabelReprintRequestService` is the only writer of `label_reprint_requests` (PENDING → APPROVED | REJECTED, APPROVED → PRINTED). Anyone holding `inventory.goods_receipts.manage` (the permission that prints the sheet) REQUESTS named serials (1–25, reason ≥20, checked at request; a serial already on an open request is refused, `REPRINT_ALREADY_REQUESTED`, under `AdvisoryLock.LABEL_REPRINT` per consignment); a DIFFERENT person holding `warehouse.labels.reprint` approves or rejects (`REPRINT_SELF_APPROVAL`; reject needs a reason ≥10); only the REQUESTER prints (`REPRINT_NOT_REQUESTER`), ONCE (`REPRINT_ALREADY_PRINTED`), within 24 h of the approval (`REPRINT_APPROVAL_EXPIRED` — derived from `decided_at`, never stored; the TTL is a code constant so it cannot be widened from settings). Every move is a guarded `updateMany` on the status read; the print claim, each unit's `LABEL_REPRINT` ledger event and the consignment timeline are one transaction, audited HIGH `consignment.labels_reprinted` with requester and approver. Approvers are told in-app (topic `label_reprint.requested`, mutable). **Not yet:** an e2e proving two approvers or two print presses race safely against a real database (the guards are there, only mocked tests cover them), a cross-consignment pending queue, and a requester withdrawing their own request.

**LBL-4 (2026-09-04): a parcel cannot be packed unless its contents were scanned.** `PackService.complete` refuses without a CLOSED `pack_box` for the shipment (`PACK_VERIFICATION_REQUIRED`), and the claim is NOT consumed on refusal so the parcel is still there to pack properly. **The gate is the closed box itself, not a setting** — the box IS the evidence the scan happened, and it costs the real flows nothing: `PackBoxService.close` closes the box before calling complete, and the STRICT-mode resume (close refused `UNIT_SCAN_REQUIRED`, operator returns with serials) also has a closed box behind it. What it stops is the naked API call, which is how every parcel in production had been packed (7 packed, 0 pack_boxes) — a bench built to verify contents that had never once run. **The escape hatch is `POST /warehouse/packs/:id/force-complete`**, a SEPARATE endpoint carrying `warehouse.pick.supervise` so a packer cannot waive the check they are performing, a reason ≥20 chars, and a DISTINCT audit action (`warehouse_pack.completed_unverified`, HIGH) rather than a flag on the normal one — "how often are we bypassing this" has to be answerable by filtering. Surfaced on the pack station as "These products have no labels to scan", for the real case: goods shelved before labelling existed. **E2E: `packAtBench()` in the harness drives the real box ritual (open → scan each line by SKU code → close); do NOT route suites through `force-complete`**, or the only spec exercising the real path is the pack-box one, and the conservation traces would be running a path production should not use.

**Warehouse scanning rules (SCAN-1 through SCAN-3, 2026-09-04 — NON-NEGOTIABLE).**

1. **SCAN-1: a REPEATED box stops the person who scanned it, and stays stopped until an admin says otherwise.** Scanning a parcel that is already packed (at the pack bench) or already with the courier (at the handover bench) is not a harmless retry: it means either a DUPLICATE LABEL exists — two physical boxes carrying one AWB, one of which will be delivered to nobody — or the operator is working from a pile that has already been done, in which case the rest of that pile is suspect too. Both get more expensive the longer they run and neither is visible to anyone but the person holding the box. `ScanBlockService.refuseDuplicate` raises a HIGH `WAREHOUSE_SCAN` system issue carrying `blocksScanForStaffId` and throws `DUPLICATE_SCAN`; `assertNotBlocked` then refuses that operator at the TOP of every scanning entry point — **the next parcel too, because the pile is what is in doubt, not only the box that tripped it**. The clearance is an admin resolving the issue with a note on `/system-issues`: a named person, a note, a timestamp. **This deliberately REVERSES the 2026-09-03 decision to treat a repeat handover scan as an idempotent no-op** — that optimised for the operator unsure whether the first scan registered, which the on-screen session list already answers, at the cost of hiding the duplicate that matters.

2. **SCAN-2: the stop is PER OPERATOR, never per station.** Four packers work in parallel and a van is loaded while the next order is still being packed; halting the building because one bench hit a duplicate costs far more than the duplicate does. The block is keyed on the staff member (`@@index([blocksScanForStaffId, resolvedAt])`, read on every scan) and the incident is keyed on the PARCEL (`duplicate-scan:<flow>:<shipmentId>`), so the same box scanned by two people is one problem seen twice. It is NOT scoped to the bench though — somebody whose pile is in doubt at pack must not walk to the handover table and carry on. **`assertNotBlocked` FAILS OPEN**: a warehouse that cannot pack because a query failed is a worse outage than a missed duplicate, and the duplicate resurfaces at the next scan anyway.

3. **SCAN-3: a scan gun firing twice is NOT a repeated box.** A reader types the code and presses Enter itself, sometimes twice; both calls read the parcel before either stamps it, so both pass the duplicate check and race at the transition. `recordHandoverScan` catches the losing transition, re-reads the order, and converges when it is already DISPATCHED — a genuine failure still throws. Without that distinction the bench would be blocked several times a day for a hardware quirk, and **a stop that fires on noise is a stop people learn to route around.** The genuine duplicate is the one where the parcel was ALREADY terminal before the scan began.

**When adding a new scanning surface, call `assertNotBlocked` first and route its "already done" branch through `refuseDuplicate`** — a bench that silently succeeds on a repeat is the hole this closes. Any table holding a block MUST be cleared in the e2e reset (`resetAuthState` truncates `system_issues`) or one test's duplicate stops every later test at its first scan.
