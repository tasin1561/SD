## apps/marketing — the COURIER redesign (MKT-1 through MKT-5, 2026-09-21)

Branch `feat/marketing-courier-redesign`, not deployed; design `docs/design-direction.md` (v3), plan `~/.claude/plans/silly-bouncing-cloud.md`. The rules that hold whatever phase the page is in:

1. **MKT-1: colour is a SEMANTIC token, never a raw step, and the four theme blocks are a GATE.** Raw scales (`--{hue}-50…950`, eight hues) live ONCE in `src/app/scales.css`; `src/app/theme.css` chooses a step per role and per theme — `--{hue}-text`, `--{hue}-fill` + `-on-fill` + `-fill-hover`, `--{hue}-tint` + `-on-tint`, `--{hue}-line`, `--{hue}-glow` — in exactly four blocks (light ×2, dark ×2). `scripts/check-theme.mjs` runs in `postbuild` and fails on a pair that differs, a hue missing a role, a `var()` nothing declares, or `--page` disagreeing with `src/lib/theme-colors.ts` (the hex the `theme-color` metas need). The steps: light text 700 (saffron, green, teal, magenta, red) / 600 (blue, violet); dark text 400; primary fills blue-600 + white; green/teal/magenta/red solids 700 + white; **saffron solids are the bright 400 with slate-950 text — never a brown carrying white**; tints 50 + 700 (magenta 800) light, 950 + 400 dark. Magenta turns to plum from 800 so its dark tint is not red-950. Text on `--corridor-gradient` is ALWAYS slate-950, both themes (7.95 worst case); white is never used on it (1.67 over the gold) and there is no "strong" variant — its 700-level midpoint was olive running to brown (owner, 2026-09-21). A button on the gradient is a slate-950 fill with white text, or a white surface card. Warning and danger always carry an icon.
2. **MKT-2: ONE type family, and headings read the face VARIABLE.** `--font-sans-face` is set by the layout's `next/font/local` call (Plus Jakarta Sans — FINAL, owner 2026-09-21; the file is committed). `body` and `h1–h4` reference `var(--font-sans-face)` DIRECTLY — a `var()` inside a custom property is substituted where that property is declared, so `var(--font-sans)` would have carried the root's face into a subtree that overrides it (the Phase 0 specimens rendered every heading in Plex for exactly this reason). Figures use the `tabular` utility.
3. **MKT-3: a dev route is `page.dev.tsx` and is NOT COMPILED in production.** `pageExtensions` lists `dev.tsx` only when `MARKETING_DEV_ROUTES=1` (`pnpm dev`, `build:preview`); a plain `next build` never sees it, so nothing leaks into shared chunks. The placeholder ribbon renders only under `NEXT_PUBLIC_PLACEHOLDER_RIBBON=1` (`build:preview`). `scripts/screenshots/render-swatches.sh` proves both after every render: no `out/dev`, no ribbon string in `out/`.
4. **MKT-4: content lives in `src/content/site.ts`; a business figure is `dummy()` until the owner supplies it.** `platform` is what the product does and may never be a placeholder; `business` is every figure, partner, hotline and testimonial, each wrapped. `pnpm check:content` lists the remaining ones by key and exits 1 while any remain (deliberately NOT in the build). `jsonLd()` refuses a placeholder inside structured data at build time. `features.newsletter = false` renders no form — never a fake success.
5. **MKT-5: the budgets are a gate, and screenshots never come from `next dev`.** `scripts/check-bundle.mjs` (`postbuild`) fails on first-load JS > 170 KB gz, three.js in first load or > 220 KB lazy, `out/index.html` > 70 KB gz, inline SVG > 700 KB, the sans woff2 > 35 KB, above-the-fold transfer > 350 KB. Renders and local specs use `build:preview` / `build` + `scripts/serve-static.mjs`, one server, killed by trap — five `next dev` servers at ~1.2 GB each is what OOM'd the machine. `apps/marketing/playwright.static.config.ts` runs the marketing + shared specs against the export; it ignores `.claude/worktrees/**`, where stale agent checkouts carry their own `@playwright/test` and load it twice.

6. **MKT-6 (Phase 3, 2026-09-21): the hero's art is the EXISTING 2D corridor map, and the three.js scene is dormant.** The owner chose `CorridorConsole` — the theme-reactive canvas map the site already carried — over the raw-three scene built for the spike ("use the existing dark and light theme map animations"). `src/three/scene-core.ts` + `hero-scene.tsx` + the `hero-3d-loader` are kept compiling and UNREFERENCED, so the bundle gate reports 0 KB of three; delete or revive them by decision. The console now follows BOTH theme triggers through `src/lib/theme-tokens.ts` (`subscribeThemeTokens`: the `data-theme` toggle AND the OS preference flipping under an unpinned page — it missed the second for months) and defers its FIRST frame to `requestIdleCallback` (the coastline render sat inside the hydration task as ~80 ms of TBT). **The hero's LCP is TEXT** — `p.hero__sub` — never the canvas (`e2e/vitals.spec.ts` pins it at 360×780, with the action card and trust row above the fold). ~~`experimental.inlineCss: true`~~ was replaced on 2026-09-21 by `scripts/critical-css.mjs` (MKT-7): each client component's CSS import had become its own render-blocking `<link>`, and inlining EVERY sheet put the whole CSS in the HTML; index.html is now ~79 KB gz against a 75 KB owner gate held provisionally at 88 (PHASE-8-MUST-FIX item 6) — **watch that ceiling as sections land.** `scripts/serve-static.mjs` gzips text when the client accepts it, because production's Caddy runs `encode zstd gzip` and Lighthouse against an uncompressed copy simulated three times the bytes (the 30 KB home page read as 230 KB). Lighthouse mobile (Slow 4G, 4× CPU) on the final build: home page perf 97 / a11y 100 / bp 100 / seo 100, LCP 2.3 s, CLS 0, TBT 140 ms; the hero-only isolation route measured perf 91, LCP 1.9 s, and was deleted after measuring, as agreed. `scripts/lighthouse-hero.sh <route…>` and `scripts/screenshots/render-hero.sh` are the harness; both bring one server and kill it on exit. A component that spreads `...rest` LAST (`RollingLabelButton`) must be WRAPPED for layout, never given a `className` — it replaced `mi mi-roll` and unrolled the label strip in the first render.

7. **MKT-7 (Phases 4–8, 2026-09-22): the page is server HTML plus near-gated islands, and the CSS pipeline is a post-build script — four rules, each learned the hard way.** (a) **Critical CSS is EXTRACTED, not inlined wholesale.** `scripts/critical-css.mjs` (postbuild, re-runnable on a processed `out/`) inlines the rules the fold's markup uses (hero + the next section + the fixed chrome after `</footer>`, minus React's streamed `<div hidden id="S:n">` segments), converts every stylesheet `<link>` — BOTH shapes, Next's `rel`-first and React Float's `href`-first `data-precedence="dynamic"` — to a low-priority preload that flips to a stylesheet on load, and strips Next's preload hints for lazy chunks. It also runs a **containment pass**: `overflow*` declarations for every class ANYWHERE on the page. Without that, a no-wrap row already styled by a critical rule (the FAQ's 774 px tab pill) sat in a container whose `overflow-x: auto` was deferred, the document went wider than the screen, Chrome's MOBILE layout viewport grew to fit it (412 → 790 px), and the fixed bottom bar jumped 750 px when the sheet landed — CLS 0.066, and `overflow-x: clip` on the root does NOT prevent it. Never concatenate the deferred sheets into one file: React Float looks for the page's own stylesheet hrefs at hydration and re-inserts any it cannot find. (b) **A below-fold island is near-gated** — `dynamic()` whose factory awaits `nearGate(id)` (`src/lib/near-gate.ts`), wrapped in `NearLoader`, so the chunk is fetched and the subtree hydrated only when the section approaches; server-rendered as usual. **The `loading` option is LOAD-BEARING**: next/dynamic wraps an SSR'd component in a Suspense boundary ONLY when a loading component is given (`hasSuspenseBoundary = !ssr || !!loading`); without it the pending gate suspends the page segment and NOTHING on the page hydrates, with no error anywhere — the theme toggle and hero tabs simply never appear (found by `theme.spec` and `hero-fit.spec` going red together). (c) **`.sec` carries `content-visibility: auto`** (the hero is `.hero`): a CPU profile put JavaScript at ~1 s of a 7 s window; the rest was style and layout of ~500 KB of HTML, one 700 ms task when the sheets landed. A full-page screenshot of such a page must expand the viewport, wait, THEN capture, or the unseen sections come out blank. (d) **A font loads for reasons that are not text**: Tailwind's preflight styles bare `<code>` with `--font-mono`, and an `<input>` loads its font for its own metrics while empty — the mono's 40 KB file downloaded on every first paint for a placeholder and some mock `<code>`; bare code now gets the system mono and the fields take the mono face only once they hold a value. **The local static server sends `immutable` for `/_next/static/`** as Caddy does — under `no-store` the sans font downloaded twice in every local Lighthouse run and the numbers were wrong for weeks. **Lighthouse's LCP here is a simulation figure**: with every font blocked it still reports 2.6 s while its own trace paints at 208 ms; Lantern counts the 146 KB of first-load JS requested before the paint. Report the emulated-device paint (0.6–0.9 s at Slow 4G + 4× CPU) beside it, and never chase the simulated number with `font-display: optional`. **Sub-agents on this branch** own disjoint files (one section or vignette: component, CSS, `src/content/sections/<name>.ts`), write code only, never run a build or a browser; the main agent owns every shared file and runs ONE verification pass — the Phase 6 hydration bug above was in a file the main agent wrote, not theirs.

## Creative authority (landing page / apps/marketing)
Fable has FULL creative freedom over aesthetics: layout, style direction, color exploration,
typography, animations, 3D. The skydrop-design skill is now a REFERENCE for brand identity,
not a constraint. Use ui-ux-pro-max's design intelligence freely, including generating a
design system.

NON-NEGOTIABLE constraints (these are still law):
1. Brand anchors: it must read as "Skydrop" — sky-blue as a core accent, dark-leaning,
   logistics/precision personality. Beyond that, go wild.
2. Performance: Lighthouse mobile ≥ 90 all categories. First-load JS < 170KB (lazy 3D chunk
   allowed). LCP < 2.5s on simulated 4G. No Lottie, no video backgrounds.
3. Responsive: flawless at 360px, 768px, 1440px. Touch targets ≥ 44px. 360px is the primary
   audience (budget Androids in BD/IN).
4. Accessibility: prefers-reduced-motion fallbacks for EVERY animation, keyboard focus
   states, semantic HTML.
5. All content/copy facts stay truthful to the product (COD call-confirm, WMS, Delhivery,
   remittance, invite-only beta).
6. pnpm only. All new deps go into apps/marketing via pnpm --filter.
7. 21st.dev: search/install tools only — generation is blocked, never attempt it.
