- **Module 15** — Pricing Engine (calculate only, no billing). - **Security + bug-hunt pass (2026-07-27).** Two rounds of adversarial end-to-end testing across the whole system, then a hardening pass. Nine real bugs found and fixed; the recurring shape is worth internalising: **an irreversible or money-moving act guarded by a check that reads OUTSIDE the transaction doing the write.** Read-then-write under READ COMMITTED is not a guard — two concurrent callers both read the pre-state and both proceed. Every fix is the same move: put the guard INSIDE the write as a `updateMany`/`WHERE` predicate on the state it read, and treat `count === 0` as "someone else got there first".
  - `TicketService` double-refund — the transition read `ticket.status`, then the refund wrote a wallet credit; two concurrent resolutions paid the seller twice. Fixed with a claim (`updateMany where {id, status: existing.status}` → `TICKET_ALREADY_MOVED` on 0). The same shape was fixed in withdrawal resolution and the accrual sweep.
  - `courier_pickup_requests` had an UNCONDITIONAL unique on `(courier, warehouse, date)`, which is STRICTER than Delhivery's actual rule ("one OPEN request per location per day"): a warehouse whose morning collection was already CLOSED could not book an afternoon van. Now a partial unique `WHERE status IN ('requested','failed')`. **A mocked Prisma has no index to violate**, so every unit test asserted the duplicate-while-open case — which BOTH versions get right. Only a real database says which is correct; that is the argument for `courier-ops-flow.e2e-spec.ts`.
  - `EmailDispatchService` rethrew a notification_logs write failure that happened AFTER a successful Resend send, so BullMQ retried and the recipient got the mail up to 5×. A ledger failure after a successful send is now logged at ERROR and reported SENT. Also added a `limiter` to the email worker (Resend caps at 2/s).
  - Verified-absent, not assumed: no IDOR (`tenant-isolation.e2e-spec.ts` — two real sellers reaching for each other's orders / customers / tickets / addresses / API keys / webhook signing keys, plus seller-token-on-admin, tampered JWT, alg=none); no SQL injection (the only raw interpolation is a range-validated server-clock year); login throttled 5/15min on email+IP; no secrets in the repo.   - **Browser security posture.** Static headers (HSTS / nosniff / X-Frame-Options DENY / Referrer-Policy / Permissions-Policy / COOP / X-DNS-Prefetch-Control) live in `packages/config/security-headers.mjs`, imported by all three server-rendered apps. The **CSP is separate and lives in middleware** (`packages/config/csp-middleware.mjs`) because it carries a per-request nonce — a static `script-src 'unsafe-inline'` does not stop injection at all, and FE-1 keeps the access token in JS memory with no HttpOnly wall around it, so a script that runs can read it. `'strict-dynamic'` is required: Next's nonce'd bootstrap inserts further chunks that carry no nonce of their own. **Never emit a CSP from both places** — the browser enforces every CSP header it receives, and the intersection of a nonce policy and an inline one blocks Next's own scripts. Next stamps its OWN scripts with the nonce automatically; a hand-written inline `<script>` is on you — read it off the `x-nonce` request header middleware forwards (`apps/track/src/app/layout.tsx` is the worked example). `apps/marketing` is `output: 'export'` so `headers()` never runs there; **the droplet runs Caddy, not Nginx** (`docs/infrastructure.md` claimed Nginx for months and never was — that stale line is what sent the first attempt at this down the wrong path), and the marketing block is `docs/caddy-security-headers.md`. The proof that a nonce CSP is correct is not the header — it is that the app still hydrates. `e2e-shared/csp.spec.ts` is that check and runs against EVERY Playwright project: zero console CSP violations + hydrated + `script-src` nonce-bearing with no `'unsafe-inline'`. It lives in `e2e-shared/` rather than per-app precisely because `apps/track` shipped a blocked inline theme script while the browser job covered only admin and seller — a frontend that is a project inherits the check by construction. **`apps/marketing` is the ONE project it skips, and the skip is stated out loud** (`SERVES_OWN_CSP` + a named reason that prints on every run): a static export has no server to set a header and no middleware to mint a nonce, and its Caddy policy carries `script-src 'unsafe-inline'` on purpose because an export's own hydration scripts are inline and can never be nonced. Serving an imitation of the Caddy block locally would let CI report a policy nobody deployed as verified — so marketing's headers stay checked against production by the curl in `docs/caddy-security-headers.md`, not by this job. **Any future static-export frontend inherits that same exemption and must state it the same way.**

    **A `Permissions-Policy` beats a site permission, and it fails SILENTLY (2026-09-08).** The shared header denied `camera=()` — an empty allowlist, which excludes our own origin too. So the pack bench and the handover bench shipped a camera button that could never work: `getUserMedia` rejects with `NotAllowedError` BEFORE the browser can prompt, Chrome's own site setting reads "Camera — allowed", and granting it by hand changes nothing because a document policy is not something a site setting can override. It presents exactly as an operator refusing a prompt they were never shown. apps/admin now sends `camera=(self)` via `permissionsPolicy({camera:true})` + `withHeader`; the other three keep denying it, because a capability nothing uses should not be reachable from an injected script. **`(self)` grants nothing** — the browser still asks. Pinned by `apps/admin/src/tests/camera-permissions-policy.test.ts`, which reads the config rather than a response: the header is set at build time, so that is the earliest point the mistake is visible, and seeing it in behaviour needs a real browser. **When a browser capability is added to a page, check this header in the same change** — every other feature here is denied by default, so the next one will land the same way.
