## Scaling & capacity (2026-08-03)

**SCALE-1: exactly ONE API process may own the background queues.** All 16 in-process BullMQ workers start themselves in `onModuleInit`; two instances would fire every cron twice and register duplicate delayed jobs. `WORKERS_ENABLED` (env, default true) gates them via `WorkerRoleService.shouldStart()`, and **every new worker MUST call it before `new Worker(...)`** — `worker-role.spec.ts` enforces this structurally by reading every `*.worker.ts`, because a worker that forgets behaves perfectly on one instance and silently double-fires on two. To scale horizontally: start additional API processes with `WORKERS_ENABLED=false`, and raise `capacity.api_instances` so the connection gauge stays honest.

**SCALE-2: connections are the binding constraint, not rows.** The managed database is 1 GB RAM / **25 connections** / 10 GB disk, and ~10 connections are held permanently by DO's own agents (pghoard, pg_cron, system-stats, TimescaleDB workers). Each API instance takes a Prisma pool of `cpus × 2 + 1` (5 on the current droplet). At idle with zero orders, production sits at 17/25. Adding instances requires either a bigger plan or PgBouncer in transaction-pooling mode (`pgbouncer=true` in the Prisma URL — prepared statements need it). Our advisory locks are transaction-scoped so they survive transaction pooling.

**SCALE-3: `/system/capacity` is the monitor** (`system-capacity` module, SUPER_ADMIN, LEAF — exports nothing, and nothing in the product may make a decision from its numbers). **Ceilings that the system cannot know are `capacity.*` system settings** an admin maintains when the plan changes; usage is measured live. The page states which is which — a guessed ceiling reads plausibly and is worse than one that admits it is unknown. Every metric carries a `consequence` and a `remedy` in prose: these failures arrive as an outage rather than a trend (a full disk works perfectly then refuses every write; the 26th connection errors while 25 are fine), so a bare percentage just moves the problem to whoever reads it at 3am. **When adding a metric, write both sentences.**

## Backups & recovery (BACKUP-1, 2026-09-15)

**Everything that cannot be rebuilt from git is copied off-site, encrypted, every hour — and a stopped copy is LOUD.** `scripts/backup/skydrop-backup.sh` runs from the `skydrop` user's crontab on the droplet (10 minutes past every hour, UTC — every two hours until 2026-09-16, every six hours before that): `pg_dump` 18 of the database (checked with `pg_restore --list`), a secrets bundle (`.env`, Caddyfile, the pm2 / Shiprocket-tunnel / Shiprocket-VPN / VPC units, the tunnel's SSH key, the NordVPN access token and the gluetun env derived from it, crontab, and the India egress droplet's settings pulled over ssh), and a mirror of the Spaces bucket — all through an rclone **crypt** remote into the owner's Google Drive (`drive.file` scope, folder `skydrop-backups`), each upload read back and compared by sha256. Retention: 7 days whole, then daily 30 d / weekly 12 w / monthly 24 m; overwritten or deleted stored files are kept 180 days. **Each run writes `system.backup.completed` / `system.backup.failed` to `audit_logs`**, and the API's leaf module `backup-watch` (hourly, SCALE-1) raises HIGH `backup-failed` (latest run failed) or `backup-stale` (no success in 3 h — two missed runs; `BACKUP_STALE_AFTER_HOURS`, which must stay a run-interval clear of two missed runs or a slow run raises an issue that then resolves itself) and clears them itself. **A change to the schedule is TWO places — the droplet's crontab and that threshold** — plus the wording in this file, `docs/disaster-recovery.md` and the script's own header; the crontab is the one the repo cannot prove, so read it back (`ssh skydrop crontab -l`) after changing it. **The passphrase is NOT in Drive**: `~/.config/skydrop-backup/passphrase` on the droplet and with the owner — without it the copy cannot be opened. DigitalOcean's own managed-database backups include **point-in-time recovery to any transaction in the last 7 days, on this basic tier** (confirmed in the panel 2026-09-15 — this file and infrastructure.md had said PITR needed a tier upgrade), so a damaged database loses next to nothing; the Drive copy is for when DigitalOcean itself is unavailable; Spaces object versioning is ON (2026-09-15) with a 90-day expiry of old versions (`expire-old-versions-90d`) — a delete through the app leaves a delete marker, not a loss; droplet backups are ON (2026-09-15; usage-based, daily 00:00–04:00 UTC, 7 days); a standby node (failover, roughly double the database cost) is the owner's call. Procedures, measured restore times and the practice-restore log: `docs/disaster-recovery.md` (first practice restore 2026-09-15: restore 4.2 s, 18/18 tables identical). **Rules:** a new place that stores data outside Postgres or the Spaces bucket must be added to the backup in the same change; never move the passphrase or the rclone config into the repo or into Drive; and a change to the backup script is proven by a manual run on the server (`~/app/scripts/backup/skydrop-backup.sh`, then read the audit row), not by `bash -n`. **Setting the crypt password: `password="$(rclone obscure …)"` with `--no-obscure`, ALWAYS** — `rclone config create` stores a password that already LOOKS obscured (base64-ish) verbatim, so it silently becomes a different key; the first password (openssl base64) did exactly that and was replaced the same day. **The Drive remote uses Skydrop's OWN Google OAuth client** (Cloud project `skydrop-508714`, Desktop client, published *In production* — left in *Testing*, Google ends the sign-in every 7 days and `backup-stale` fires weekly); it replaced rclone's shared client, which rclone retires during 2026. Under `drive.file` a different client cannot see files another created, so changing the client means a fresh folder.
