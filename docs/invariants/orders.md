**Order rules (ORD-1 through ORD-10 — NON-NEGOTIABLE):**

1. **ORD-1: Lifecycle state machine.** `OrderStateMachineService` — 29-status declarative transition matrix (Module 7 added `REJECTED_BY_CUSTOMER` + `REJECTED_NDR` reject terminals; R5b added the `AWAITING_SELLER_DECISION` pause); no any→any. **Matrix-declared self-loops are valid event-writing transitions** (Module 7: `CALL_NO_RESPONSE→CALL_NO_RESPONSE`, `CALL_RESCHEDULED→CALL_RESCHEDULED` — "same state, a new attempt was logged"); `transitionStatus` lets `from===to` through ONLY when the matrix declares it, else 409 NOOP_TRANSITION. Critical property: pre-confirmation cancels carry NO stock release (nothing was reserved yet — see ORD-10).

2. **ORD-2: God mode is the ONE sanctioned bypass.** `OrderAdminOverrideService.forceMutate()` only. Guardrails: reason ≥30 chars, `acknowledgeDataIntegrityRisk` literal `true`, ≥1 of `fieldChanges`/`targetStatus`; DB + event + audit in one tx; `hasAdminOverride` set-once-NEVER-cleared; audit severity CRITICAL. Opts OUT of saga compensation (reserve attempted-not-blocking on →CONFIRMED; away-from-CONFIRMED leaves reservations — cleanup via `release-reservations` endpoint). **AMENDED 2026-09-12: a forced status has the same consequences as a transition, except stock.** A real status change writes a STATUS_CHANGED row (`data.source = 'ADMIN_OVERRIDE'`) beside its note and runs `OrderPostCommitHooksService.runForStatusChange` — the SAME method `transitionStatus` runs: CC-6 enqueue/dequeue, the pack-eligible audit on PICKED, a shipment provisioned on CONFIRMED (read from the committed row) or voided on a cancel/reject terminal, the cancel-time ORDER_CHARGES refund, and the lifecycle-bus emit LAST (`source: 'ADMIN_OVERRIDE'`), so notifications, outbound webhooks, invoices, delivery-time money and the AWB booking all react. The refund is judged on HISTORY for god mode (no refund if a shipment was handed over or the order reached a post-dispatch status through a transition not stamped ADMIN_OVERRIDE), on `from` for a transition. A listener deciding on the EDGE must read `source` — a forced edge may be one the matrix forbids. A field-only or no-change edit runs none of it. Stock stays opted out: the hooks service has no stock dependency and the stock steps belong to `transitionStatus` alone. `order-post-commit-hooks-shared.spec.ts` pins that both writers call it and neither runs a hook itself; **a new non-stock post-commit hook goes in that service, never in one writer.** **AMENDED 2026-09-19: a money-affecting FIELD change reaches the same service.** God mode may write `codAmountInr` and `paymentMode`, and called the reseller re-pricing nowhere — a forced COD left the order saying one figure while the store's and the seller's credits were worked out from another, silently. `runForMoneyAffectingEdit` is the SECOND entry point on the shared service, and both writers of a money-affecting field call it (`OrderService.edit` and `forceMutate`, pinned by the same spec, which also refuses either of them calling `recalculateAfterEdit` itself); `MONEY_AFFECTING_ORDER_FIELDS` is declared there so the two cannot disagree about what moved the money. God mode runs it BEFORE `runForStatusChange`, because the lifecycle emit is what sets a credit running and a plan corrected afterwards is corrected after the stale figure was paid. **The force is never refused — where the money cannot follow it is LOUD instead**: `RESELLER_CREDIT_ALREADY_PAID` raises HIGH MONEY `reseller-money-diverged:<orderId>` naming what each party was actually credited, and is NEVER retried (a paid credit will be paid tomorrow too — the TRK-10 rule); anything else raises `reseller-money-stale:<orderId>`, which the hourly `OrderAttentionService` sweep retries through `OrderWriteService.retryResellerMoneyRecalculation` (the open issues ARE the worklist — nothing on the order records "needs pricing", and a column for it would be a second source of truth). Both clear on any later success; the refusal is on the force's own response and on the god-mode result panel; and BOTH parties are told — the store by email, seller staff in-app — because neither of them made the change. `forceMutate` writes guarded on the status it READ (`updateMany where {id, status: from}` → 409 `STALE_ORDER_STATUS`) — it still bypasses the matrix, but a stale force can no longer interleave with an agent's confirm. Provisioning is serialised per order (`AdvisoryLock.SHIPMENT_PROVISION`, rechecking for a live shipment inside it), so two writers of CONFIRMED cannot create two parcels.

3. **ORD-3: Status changes via `OrderWriteService.transitionStatus()`** — the sole cross-module WRITE boundary. Order row + events + audit are one tx. The stock side-effect is a **SAGA** (M5 INV-1/INV-6 owns its own tx, takes no tx param): RESERVE pre-tx (fail→OUT_OF_STOCK / 409; tx-fail→compensating release); RELEASE/FULFILL post-commit idempotent (mirrors INV-5).

4. **ORD-4: `OrderEventWriterService` is the only writer of `order_events`**, append-only (no update/delete path by construction).

5. **ORD-5: SOFT recipient validation** — format checks (PIN, E.164 phone) + `ops.allowed_indian_states` membership only; no PIN↔state cross-check (deferred). **AMENDED 2026-08-07: city and state are OPTIONAL, and the seller order form no longer asks for them.** Delhivery routes on the PIN and resolves the locality itself, so making a seller type what the courier already knows was two chances to disagree instead of one fact. Consequences, stated rather than discovered later: (a) the allowed-states membership check **cannot run** on an order that carries no state — it is not bypassed, there is nothing to check, and an order for a state we do not serve will now be caught by Delhivery's serviceability rejection (CUR-5, reactive) instead of at create; (b) `recipient_city` / `recipient_state_province` stay NOT NULL and store `''` — deliberately not made nullable, because that would push null-handling through ~15 readers (tracking projection, invoice, Delhivery payload, shipment snapshot) to express something `''` already expresses; (c) the public tracking page's destination city and order-list location are blank for these orders. An order that DOES carry a state (CSV import, admin) is still validated exactly as before. **Also 2026-08-07: `recipientAddressLine2` is REQUIRED on create** (`@IsNotEmpty`) and may not be cleared on update — it now holds the landmark, and the landmark is the field that decides whether a rural address is findable. The separate `recipientLandmark` column survives for CSV import and pre-existing orders, but **nothing sends it to the courier**: the Delhivery address is built from line 1 + line 2 only, which is why the landmark had to move onto line 2 to reach a driver at all. **UNPROVEN and worth watching at go-live: whether Delhivery accepts a manifestation with empty `city`/`state`.** No real write has ever been made against this account, so this is an assumption; `docs/delhivery-go-live-test.md` is where it gets settled.

6. **ORD-6: Immutable snapshot.** Recipient block + per-line SKU info snapshotted at order create, never re-linked. Cross-module consumers read the order's snapshot via `OrderReadService`, never re-resolve from the live catalog. **AMENDED 2026-09-18 (owner) — the snapshot is immutable against the CATALOGUE, not against the two parties to the sale.** A later price-list or terms change may never re-price a placed order, and that half is unchanged and pinned (`reseller-store-orders.e2e-spec.ts`). But an order is a record of what is being sold, and the people selling it may correct it: on a RESELLER store's order both Seller staff and the store may change the products, the quantities, the retail inside the agreed range, the money the customer pays and the customer's details, until the lifecycle stage says otherwise (`CONTENTS_EDITABLE_STATUSES` for the contents; `recipientChangeRoute` for the address). Every such change writes an order event, tells the party who did not make it, and recalculates the money through `ResellerOrderMoneyService` under the terms the order was PLACED on. A REPLACED line keeps its own snapshotted transfer price and range (`ResellerOrderRetermService`); an ADDED line is priced from that store's catalogue and refused by name when it has no price there — never given one we made up. See `docs/reseller-stores.md` "Both sides may change the order".

7. **ORD-7: Per-seller customer identity** — `@@unique(sellerId, phoneE164)`. Phone immutable once set (no mutation path by construction). Cross-seller customer dedup deferred (Phase 1A privacy choice). **AMENDED 2026-09-14 (RS-5): identity is per OWNER — the seller, or one of their reseller stores.** `customers.reseller_store_id` (nullable); the unique is now two PARTIAL uniques (`(seller_id, phone_e164) WHERE reseller_store_id IS NULL`, `(reseller_store_id, phone_e164) WHERE … IS NOT NULL`), so `CustomerService.findOrCreate` is find-then-create under `AdvisoryLock.CUSTOMER_IDENTITY` (call it inside the caller's transaction). **AMENDED 2026-09-16 (owner): the SELLER reads a reseller order IN FULL, customer included.** RS-5 masked it; `order/reseller-privacy.ts` is DELETED. The order is the seller's — their stock, their warehouse slot, their courier, their money at risk — and a seller who cannot see who a parcel is going to cannot ring about a failed delivery, judge a bad address or answer the call centre. So the recipient block is whole on `OrderService.list` / `loadOwnedForSeller`, seller search by name or phone matches reseller orders too, the reputation lookup counts every order of theirs (`CustomerScope` SELLER is no longer channel-only), and `CustomerService.list/getById` reach a store's customers. **Identity is still per OWNER — the two partial uniques stand — and the PHONE is still immutable everywhere** (it is what tells one customer from another). **AMENDED 2026-09-18 (owner): Seller staff may also EDIT one of their reseller stores' customer rows, and the store may edit its own** (`store customers.manage`, `PATCH /store/customers/:id`). `CustomerService.update` scopes on the seller and, for a store caller, on the store — a miss is a 404 that says nothing more — and the party who did not make the change is told. **DELETING is still the seller's own row only** (`getOwnById`): deleting is not correcting, and a store's customer row is its record of somebody it sold to, which its own screens read. A STORE still reads only its own. See `docs/reseller-stores.md` "Store orders as built".

8. **ORD-8: Order numbers** via per-year Postgres SEQUENCE under a txn-scoped advisory lock, allocated INSIDE the create tx. Format: `SD-YYYY-NN-XXXXXX`.

9. **ORD-9: CSV import is state-aware idempotent** by `(sellerId, externalRef→sellerOrderRef)`: new → create PENDING_CONFIRMATION; DRAFT/PENDING_CONFIRMATION → PATCH; CONFIRMED+ → error row. CSV is submission, not drafting. **AMENDED 2026-09-29 (owner): ONE ROW IS ONE LINE, and rows sharing a reference are ONE ORDER — the "single line, multi-line deferred to Phase 2" half of this rule is GONE.** It was never a deferral so much as an importer narrower than the system behind it: `CreateOrderDto.items` has always taken 1–200 lines and the portal form places multi-line orders every day. What existed was worse than unsupported — Delhivery's bulk template expresses a two-item order by repeating `*Sale Order Number`, so the second row found the first by its reference and PATCHED it, and a two-item order silently became a one-item order carrying the LAST row's SKU. `OrderCsvParserService.groupRows` is the grouping and the ONE place completeness is judged; **required fields now have TWO grains** — three a ROW must carry (`externalRef`, `productSku`, `quantity`) and the rest judged on the ASSEMBLED order, because a file may repeat the customer block on every row of an order or state it once and blank the rest, and demanding it per row refuses the second shape. `ORDER_REQUIRED_FIELDS` is DERIVED from `ORDER_CSV_REQUIRED_FIELDS` minus the row three, never restated (the drift that check exists for). **An order whose rows contradict each other is refused WHOLE**, every row of it named in the report: half an order placed is worse than none, because the seller believes the parcel holds what the file said. `applyBulkPatch` now REPLACES the line set (`BulkOrderPatchInput.lines`) exactly as `edit` does — safe only there, since it admits DRAFT/PENDING_CONFIRMATION alone and nothing is reserved before confirmation (ORD-10) — and a reordered re-upload compares as UNCHANGED.

   **ORD-9b (2026-09-29): Delhivery's own 36-column bulk template imports with the seller changing NOTHING.** That is the format sellers already have, so every column is accounted for: mapped by alias, or in `ORDER_CSV_IGNORED_HEADERS` with the reason a person reads. `normalizeHeader` collapses every run of non-alphanumerics to one space, so their `*` mandatory marker and the `(cm)`/`(gm)` unit suffixes need no aliases of their own. **An unknown column has never failed an upload and must not start** — a seller pasting a template they downloaded from their courier cannot delete the columns it requires — but "unknown" and "known and not for us" are different facts and are now reported separately, because a guessed suggestion beside `*Pickup Location Name` invites exactly the wrong fix. Three things a file from another system gets right and we used to refuse: a phone as ten bare digits (normalised to E.164 at the IMPORT boundary only — the API keeps demanding E.164, rule 2), a money cell as `₹15,000`, and a state written `Orissa`, `J & K` or `KL` (`STATE_ALIASES` in `AddressValidationService`, the ONE reader — an alias only ever resolves to a canonical name the list ALREADY allows, never a way in for a state we do not serve). **`*Payment Mode` is now a real field and is AUTHORITATIVE**; the old inference from "is there a COD amount" survives only as the fallback for a file with no such column, and the two disagreeing is an error row by name rather than a guess — it was wrong in both directions, and a row marked COD with an empty amount became a PREPAID order for a parcel the courier will still try to collect on. **`COD Amount` is the collectable; `*Unit Item Price`, `Discount Value` and `Amount Paid` are the figures it was BUILT FROM**, recorded for readback, never re-applied and never used to derive it — which is `OrderService.create`'s own contract at the write, and why a mismatch is not refused: Delhivery's own sample row states unit price 1,500 × 2 against a COD of 15,000, so refusing one would refuse their documentation. **`Shipping Address Line2` is optional for them and REQUIRED for us** (ORD-5: it is the landmark, and the courier address is line 1 + line 2) — refused BY NAME with a message that says what a landmark is for, because there is no honest fallback: the city adds nothing the PIN did not already give. **Preview runs the importer's OWN grouping over the whole file** and reports `orderCount`, `rowsWithProblems` and the first reasons; column mapping was all it used to check, and that is not what a file from another system gets wrong — Delhivery's template maps every required column and leaves our landmark blank, so the upload previewed perfectly and failed every row.

10. **ORD-10: Reservation is LATE.** NO stock reserved at order create (no availability check at create — M7 catches at confirm). Reservation is created only on entry to CONFIRMED via the M5 saga pattern in ORD-3. **AMENDED 2026-09-14 (RS-5) — one check at create, for a reseller store's order only:** a line may not ask for more than the store is SHOWN (`RESELLER_QTY_EXCEEDS_VISIBLE` — the catalogue's visible quantity, hidden share and set-asides included), or the hidden share would mean nothing. Still no reservation and no real-availability refusal at create; real stock is judged at confirmation, where every order (channel too) now reserves through the reseller set-aside guard (RS-5 below). A reseller order takes no at-placement hold (R5).

**Status-change rules (general):**
1. Any status-change service wraps update + side-effects (token revoke, note, audit, email enqueue) in one `prisma.$transaction` — EXCEPT where a cross-module service owns its own tx (e.g., M5 stock services), in which case use the SAGA pattern (see ORD-3).
2. Email enqueue happens INSIDE the transaction. Phantom-job edge case (commit fails after enqueue) handled by consumer-side idempotency.
3. Strict transition guards: each direction has exactly one valid source state. No "any → any" transitions.
