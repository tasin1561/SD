**Notification rules (Module 11 — NOTIF-1 through NOTIF-8, NON-NEGOTIABLE):**

1. **NOTIF-1: Best-effort, NEVER blocks / rolls back the transition.** The order lifecycle emit is a POST-COMMIT hook (the 6th in `OrderWriteService.transitionStatus`, after CC-6 dequeue + shipment-provision void + audit chain); the bus' `emit()` wraps `subject.next()` in try/catch and never re-throws. The listener handles each event via `void this.handle(event).catch(...)` — a handle() rejection is logged + swallowed at THREE layers (the bus emit wrapper, the listener subscribe wrapper, the handle() catch). NEVER make any listener-side error propagate up to the transition; the transition is the durable fact, notifications are a reflection of it.

2. **NOTIF-2: Store-then-send with composite-key dedup.** `NotificationLedgerService.enqueue()` INSERTs the notification_logs row in PENDING/QUEUED state FIRST, carrying `eventId = order_status:<statusEventId>`; the partial-unique `(event_id, recipient_type, recipient_id, channel, template_code) WHERE event_id IS NOT NULL` is the dedup gate — a re-emit on the same lifecycle event lands a P2002 the service catches and converts to `kind: 'DEDUPED'`. The BullMQ send job enqueues AFTER the row exists. `EmailDispatchService.send` UPDATEs the pre-created row (`existingNotificationLogId`) on outcome, preserving the row id as the durable dedup anchor; legacy fire-once callers (the 8+ pre-M11 sites) leave `existingNotificationLogId` unset and get the unchanged CREATE path.

3. **NOTIF-3: Fan-out independence per target.** The listener resolves N fan-out targets per lifecycle event (mapping returns 0/1/2 — seller+customer, customer-only, seller-only, or none); the listener loops, wrapping EACH `ledger.enqueue()` in its OWN try/catch — one target's failure NEVER aborts the loop or leaks into the other targets. The composite-key gate per row means a BullMQ retry on one target never touches the other; a re-emit double-sends none.

4. **NOTIF-4: Single-source mapping (THIRD instance).** `NotificationEventMappingService.resolveForOrderStatus(to)` is the SOLE owner of "order status → outbound notifications"; pure logic, no Prisma, no Order dependency. **F2 discipline:** EXHAUSTIVE TypeScript switch over every `OrderStatus` — a future enum addition fails to compile until the author consciously routes it to a fan-out list (possibly `[]`). The Q5 table is encoded ONLY here; never duplicated in the listener / controllers / other services. Joins `CallOutcomeMappingService` (CC-2) and `TrackingStatusMappingService` (TRK-5) as the three single-source mapping services in the codebase.

5. **NOTIF-5: Order module is unaware of notifications.** The order module never imports `NotificationsModule` or any notification service. The wiring goes through the R3 `OrderLifecycleEventBus` — order publishes; notifications subscribe. The bus is the dependency-free shared primitive (R3 split #4 after M5/M7/M8). A future Phase-2 multi-instance API would swap the in-process Subject for Redis pub/sub at this exact seam; the publisher / subscriber API stays the same.

6. **NOTIF-6: Dev-mode stub via empty `RESEND_API_KEY`.** No separate adapter; `ResendService` checks `env.resendApiKey` and either calls the real SDK (production) or emits `[DEV] Would send email` log lines (development + e2e). The dispatch service writes the notification_logs row regardless (status SENT in dev, status SENT/FAILED in prod). The e2e tests rely on this — they assert against notification_logs rows AND the `[DEV] Would send email` log lines, never against actual Resend delivery.

7. **NOTIF-7: Reuses the existing EmailModule substrate.** M11 ADDS the lifecycle fan-out layer (mapping + ledger + listener) on top of M1's already-built EmailQueue / EmailWorker / EmailDispatchService / TemplateRenderService + the seeded notification_templates. The substrate was NOT duplicated; the M11 ledger's CREATE-then-UPDATE pattern is the ONE extension point added to EmailDispatchService (`existingNotificationLogId` path). The pre-M11 fire-once callers (auth/seller-mgmt/inventory) are UNCHANGED.

8. **NOTIF-8: Missing recipient address lands a SKIPPED row, NOT FAILED.** A customer order with no `recipientEmail` snapshot (the ORD-6 immutable customer email) is a foreseeable Phase-1A reality (a CSV row that omitted the email, an admin manual entry that skipped it). The listener detects null toEmail at resolve time; the ledger writes a `status: SKIPPED` row carrying the same `eventId` so a re-emit STILL consumes the dedup gate (no second SKIPPED row). No BullMQ enqueue. SELLER toEmail is non-null by schema; a null SELLER address is a data integrity error, not a runtime path. Phase-2 SMS/WhatsApp will generalize "no resolvable address" to "no phone / no whatsapp number" at this same gate.

**Module 11 architecture (R3 + facade):**
- The `OrderLifecycleEventBus` PRIMITIVE lives in a standalone `lifecycle-events` module (rxjs Subject-backed, NO Order dep, NO Notifications dep; imported by both `OrderModule` and `NotificationsModule`). The FOURTH successful R3 split after `inventory-shared/inventory-stock` (M5), `call-queue` (M7), `shipment-provision` (M8). The exported surface is `OrderLifecycleEventBus` only.
- `NotificationsModule` houses the listener + the supporting services:
  - `NotificationEventMappingService` (NOTIF-4, pure logic, no Prisma — single-source mapping, third instance).
  - `NotificationLedgerService` (NOTIF-2/3/8 — store-then-send + composite-key dedup gate + SKIPPED row writer; reuses `EmailQueue` via `EmailModule` import).
  - `NotificationListener` (NOTIF-1/3/5 — the bus subscriber; `OnApplicationBootstrap` subscribes, `OnModuleDestroy` unsubscribes + DRAINS in-flight `handle()` promises; `drainInFlight()` exposed publicly so the e2e harness can quiesce listener work between tests — the M11 follow-up commit codifies this).
- Cross-module export surface: `NotificationsModule` exports NOTHING — the listener subscribes to the bus on bootstrap; no other module needs to call into M11. The listener is internal by construction.
- Email substrate (`EmailModule`) is REUSED unchanged: `EmailQueue` (BullMQ producer), `EmailWorker` (consumer), `EmailDispatchService.send` (the only extension point — the `existingNotificationLogId` UPDATE path landed in M11 commit 4), `TemplateRenderService` (Nunjucks; `throwOnUndefined: false` so unused template vars stringify to empty), `ResendService` (real SDK in prod; `[DEV] Would send email` stub when `RESEND_API_KEY` is empty).
- **No new BullMQ queue.** M11 wires its lifecycle fan-out through the existing `email` BullMQ queue / worker. The pre-M11 callers continue to use it directly (legacy CREATE path); M11 lifecycle callers go through the ledger's CREATE-then-enqueue + UPDATE-on-send flow.
- **No new HTTP endpoint.** M11 has NO public surface — the fan-out is driven by `OrderWriteService.transitionStatus`'s post-commit emit. Admin/ops resend or visibility UIs are deferred to M12.

**E2E listener drain (M11 follow-up — locked discipline):** The bus' `emit()` is synchronous; the listener spawns `handle()` async via `void this.handle(event).catch(...)`. In production this is exactly the contract; in e2e it leaks past test/suite boundaries unless explicitly drained. **TWO drain hooks must be honored:**
- `NotificationListener.onModuleDestroy()` unsubscribes FIRST then `Promise.allSettled([...this.inFlight])` — Nest awaits this in `app.close()`, so suite-boundary contamination is impossible.
- `NotificationListener.drainInFlight()` is the public BETWEEN-TEST drain — `resetAuthState(prisma, app)` calls it BEFORE the TRUNCATE cascade. Without this drain, a leaked notification_logs INSERT's FK `RowShareLock` on orders/shipments deadlocks the harness's `AccessExclusiveLock` TRUNCATE (`40P01`). Every e2e spec passes `h.app` so this is automatic; specs that don't touch orders may use the legacy single-arg form.

When adding ANY future post-commit fire-and-forget side-effect that writes via async DB calls — the same drain pattern MUST apply: track in-flight Promises in a Set, expose a public `drainInFlight()`, await in `onModuleDestroy()`. The leak shape is universal under async fire-and-forget; the M11 fix is the canonical reference.

**Notification rules (general — see also Module 11 invariants NOTIF-1..8 above):**
1. Send via BullMQ workers only. API endpoints enqueue; workers send.
2. Throttle per (recipient, template). Check `notification_logs` before send; mark THROTTLED if limit exceeded.
3. Respect seller's quiet hours for non-urgent categories.
4. **Two idempotency regimes coexist on `notification_logs`** — pre-M11 fire-once callers (auth/seller-mgmt/inventory) dedup via the polymorphic `(templateCode, recipientType, recipientId)` LOOKUP in the caller service BEFORE enqueueing; the row carries NO `eventId`. M11 lifecycle fan-out callers set `eventId = order_status:<statusEventId>` and rely on the partial-unique `(event_id, recipient_type, recipient_id, channel, template_code) WHERE event_id IS NOT NULL` (NOTIF-2). The two coexist because the partial-unique only fires when `eventId` is present. **NEW lifecycle-event fan-out paths MUST set `eventId`** (the partial-unique is their only protection). **DO NOT add `eventId` to legacy callers** without auditing their dedup logic — they currently rely on a template-code lookup that ignores `eventId`. (See phase-1a-debt M11 entry "Two idempotency regimes" for the migration path.)

**Outbound webhook rules:**
1. Sign every payload with HMAC-SHA256 using endpoint's `secretKey`.
2. Retry policy (BullMQ): 5 attempts, exponential backoff (30s, 5m, 30m, 6h).
3. Auto-disable endpoint after N consecutive failures (default 50, configurable via `system_settings`).
4. Idempotency: unique constraint on `(endpointId, eventType, eventId, attemptNumber)` prevents double-send.

21b. **Honor NOTIF-9 through NOTIF-13 (notification audience, 2026-09-04).** M11 could reach the two people an order concerned. This reaches an AUDIENCE, on more than one channel, and each rule is what stops that becoming a way to mail four thousand people by accident.

    1. **NOTIF-9: the CATEGORY decides the channels, and it sits ABOVE the recipient's preference.** `NotificationPolicyService.policyFor` is an F2-exhaustive switch over `NotificationCategory`; `resolveChannels` intersects what the caller ASKED for with what the category PERMITS, and only then removes what the person has muted. **CREDENTIAL is `[EMAIL]` and `mutable: false`** — login, signup, invite, password reset, email verification. This is structural, not a setting: a password reset you can only read once signed in is useless, an invite has no account to deliver to yet, and "your password was changed" shown in-app is seen by whoever is already inside rather than by the person being warned. Asking for IN_APP on a credential message is a category error, not a preference to honour, so it is dropped rather than obeyed; a mute on one is ignored, and `assertMutable` refuses to record one in the first place (`NOTIFICATION_NOT_MUTABLE`). A template's category comes from `notification_templates.category`, set by `categoryForTemplate()` in the seed on both create AND update — **a new credential template whose code does not match that regex silently becomes OPERATIONAL and therefore in-app-able**, which is the one way this rule can be lost. Pinned by `notification-policy.service.spec.ts` and, end to end against a real database, by `notification-audience.e2e-spec.ts` (asked for in-app directly, asked for via a broadcast, and asked for by somebody who has muted email — all three).

    2. **NOTIF-10: an audience is a SELECTOR, resolved at send time, and STAFF are addressed by PERMISSION rather than by role.** `NotificationAudienceService` owns the nine `AudienceSelector` kinds; `resolveMany` dedupes by `${subjectType}:${recipientId}`, so overlapping selectors reach a person ONCE. Prefer `STAFF_PERMISSION` over `STAFF_ROLE`: roles are rows an admin can invent, rename and delete, and a notification addressed to a role name goes quiet the day somebody reorganises the team — the permission is the durable fact about what a person does. Liveness is `deletedAt: null` (neither `SellerUser` nor `StaffUser` has an `isActive`).

    3. **NOTIF-11: the inbox is SELF-SERVICE, never a grantable permission.** `Admin`/`SellerNotificationController` carry `@StaffSelfService()` / `@SellerSelfService()` — the second entry in each app's self-service list, and each is written down with its reason in `staff-permission-surface.spec.ts` / `seller-permission-surface.spec.ts`. Two arguments, both load-bearing: every row is addressed to the caller by the id on their TOKEN and never by one in the request, so a permission would be asking a question the token has already answered; and a permission has to be GRANTED — a key added today reaches no role that already exists, so the bell would have rendered and then 403'd for most of the estate on the day it shipped. Reads and writes are scoped in the WHERE clause, never fetched-then-compared (a miss is a 404 that says nothing about whether the row exists). **Sending TO an audience is the opposite act** and lives in its own controller, `AdminNotificationBroadcastController`, behind `notifications.broadcast` — split rather than mixed because the guard SHORT-CIRCUITS the whole permission gate on a class-level self-service marker, so one controller cannot be self-service for some handlers and gated for others.

    4. **NOTIF-12: a broadcast is previewed before it is true, and the count is carried into the send.** `preview()` resolves the audience and returns the number plus five names — "send to all sellers" means nothing; "send to 4,312 people, starting with these five" is checkable. `send()` re-resolves and REFUSES on a mismatch (`AUDIENCE_CHANGED`), so the number on screen when somebody decides is the number that is true when they commit. Refusals happen BEFORE the row is written (`CATEGORY_NOT_BROADCASTABLE` for CREDENTIAL — a broadcast of a message about one person's own account is a contradiction; `EMPTY_AUDIENCE`; `NO_PERMITTED_CHANNELS`), because a guard that refuses afterwards leaves a broadcast recorded as sent to nobody. The row is `SENDING` before delivery and `SENT`/`FAILED` after (visible-vs-silent — a crash mid-send leaves a true, recoverable statement); the **audience is stored AS CHOSEN**, not as the people it resolved to, because "who did this go to" is asked a month later when the population has moved; `eventId` is `broadcast:<id>`, so a retry of the SAME broadcast cannot send twice while a genuinely new one is unaffected. Audited HIGH with the audience and the count.

    5. **NOTIF-13: per-recipient isolation, and ONE query for the mutes.** `NotificationDispatchService` writes in chunks of 200 and wraps EACH delivery in its own try/catch — on a broadcast, aborting on the first error is one bad address costing four thousand people the message. A P2002 on the NOTIF-2 partial unique is `deduped`, NOT `failed` (a re-emit is the system working; counting it as a failure pages somebody). The in-app row IS the delivery, so it is written `SENT` with `sentAt` — leaving it QUEUED would show an unread nobody ever marks sent — while EMAIL keeps M11's store-then-send through `EmailQueue` with `existingNotificationLogId`. Mutes for the whole audience are resolved in a SINGLE query, and an immutable category skips the lookup entirely.

    6. **NOTIF-14: a lifecycle notification is ONE thing on TWO channels, and the two are silenced by DIFFERENT people.** `NotificationFanOut.inApp` on a SELLER target adds the in-app leg — one optional field on the existing NOTIF-4 entry rather than a second fan-out row, because listing them separately doubles the table whose whole job is to be the single place this is decided and lets the halves drift. The listener fires both legs independently (`deliverInApp` is best-effort and isolated; an inbox line is not worth withholding because a mail server was slow), ignores `inApp` on a CUSTOMER target outright (no login in Phase-1A, so no inbox — checked rather than trusted to the table), and addresses the in-app leg with `SELLER_PERMISSION` so it reaches the people at that company the order concerns rather than all five of them. **The two legs carry different topics on purpose**: the email keeps the template code (`seller.order_dispatched.email`), the in-app leg drops the `.email` suffix. The COMPANY decides what it is emailed about, per category, at `/settings/notifications`; a PERSON decides what reaches their own inbox, per topic, at `/notifications`. One shared key would make one of those decisions silently override the other. Event ids differ by an `:inapp` suffix for the same reason — the dedup tuple already includes the channel, but distinct keys mean a later change to either leg cannot collide with the other.

    7. **NOTIF-15 (2026-09-05): a setting a seller can change has to change something.** `seller_notification_preferences` shipped in M1 with a screen behind it and, for months, exactly ONE reader — its own CRUD service. A seller could switch a category off, watch it save, and keep receiving every email. `SellerNotificationPreferenceResolver` is the consultation, and is deliberately the ONLY reader of those rows on the send path (the `BinPolicyService` / `WarehouseResolverService` discipline: five call sites each deciding what a preference means is how they come to disagree). The listener asks it once per SELLER target, before either leg. **A CUSTOMER target is never gated** — a customer is not the company, never agreed to anything, and a seller must not be able to silence the emails their own customers rely on. **It FAILS OPEN**, and a missing row means send: the two failure modes are not symmetric, since sending one email somebody switched off is a nuisance while silently not telling a seller their parcel came back is money. **CREDENTIAL is never gated and never even looked up** (NOTIF-9), so the rule holds even if a future change routes one down this path. Which category a notification belongs to is declared on its NOTIF-4 fan-out entry (`sellerCategory`) rather than in a second template-code→category table, and a spec pins that every SELLER target declares one and no CUSTOMER one does. **Quiet hours hold the EMAIL only, and hold the SEND rather than the record**: the notification_logs row is written immediately and the BullMQ job carries a delay, so a message waiting out the night is visible as QUEUED instead of looking like it was never produced. An inbox line is never held — nothing pings, and the in-app row IS the delivery. The window is read in the seller's own IANA zone through `Intl` (never a stored offset, which drifts an hour twice a year — the WAL-3 lesson) and **may wrap midnight**, which 22:00→07:00 does and a naive `>= start && < end` gets wrong in the most ordinary configuration there is. **The in-app leg runs BEFORE the email gate on purpose**: the gate `continue`s, so running it after meant switching off a category's email silently switched off its inbox line too — two independent switches, one secretly wired to the other. **SMS, Webhook and Frequency were REMOVED from the screen** (the columns survive): there is no SMS sender in Phase-1A, outbound webhooks are configured per endpoint and never read that toggle, and DAILY_DIGEST needs a scheduler that does not exist. A control that does nothing is worse than no control — somebody switches it, believes it, and finds out weeks later. **Do not re-add one without a reader on the send path.**

    8. **NOTIF-16 (2026-09-05): raising an issue TELLS somebody, and the audience is declared per kind.** `SystemIssueService.raise()` recorded a problem and notified nobody — the sweeps that call it (ATT-1's AWB loop, TRK-10's stranded tracking, SCAN-1's duplicate scan) exist to catch what nobody notices, and their output landed on a page nobody was asked to open. `SystemIssueNotifier` closes that. **Only on a NEW issue**: a recurrence bumps the count and returns before reaching it, so a job failing nightly for a fortnight interrupts one person once rather than fourteen times — a bell that rings for everything is a bell people turn off. **Only HIGH and CRITICAL**; LOW ("worth knowing") and MEDIUM ("stopped and will stay stopped") belong on the page. CRITICAL additionally EMAILS, because "drop what you are doing" has to reach somebody who is not currently looking at the admin app. `permissionsFor(kind)` is F2-exhaustive so a new `SystemIssueKind` fails to compile until somebody decides who it is for — a default audience is how a new kind of failure comes to be raised for months with nobody addressed by it. **`system.settings.view` is on every audience** because it is what opens `/system-issues`: a notification pointing at a page the reader cannot open is a dead end. The notifier swallows its own failures — every caller is already inside a failure path, and an alerting layer that throws turns a handled problem into an unhandled one.

    9. **NOTIF-17 (2026-09-05): a person picks topics from a NAMED list; they never type a code.** Silencing something used to mean typing its key into a text box, so in practice nothing was mutable and `SUBSCRIBERS` — an audience of people who opted IN — could never resolve anybody. `NotificationTopicCatalogService` is the named list, per subject type. It is **DECLARED, not derived**: deriving it would mean `notification-audience` importing `notifications`, which imports it, and the R3 rule says extract rather than `forwardRef` — but there is nothing to extract, the list is words for humans. The guarantee is `notification-topic-catalog.service.spec.ts` instead, which pins it against the NOTIF-4 mapping and against `SystemIssueKind` **in both directions** (a test can import what a module cannot — the M10 F6 technique). It caught real drift on the first run: `shipment.rto_initiated` where the sent key is `shipment.rto_initiated.seller`, a mute that would have silently done nothing. **The failure this guards is a topic on a settings page that the dispatcher never looks up**, which reads to a person as a switch they flicked that did nothing. **A topic key is the template code WITHOUT its `.email` suffix** (NOTIF-14) and `topicForIssue()` is the one place an issue kind becomes one.

    13. **NOTIF-21 (2026-09-05): "delete" in the inbox is a DISMISS, and it must stay one.** `notification_logs` is the ledger the NOTIF-2 dedup gate reads — the partial unique on `event_id`. Remove a row and a re-emit of the same event sends again, so a literal `DELETE` behind a delete button would quietly reopen the hole that unique exists to close, and it would do it invisibly (the second send looks exactly like a first). `dismissedAt` hides a row from ONE person's feed; every read path filters `dismissedAt: null`, including the unread count — hidden in the list but still counted would leave a badge pointing at nothing, which is how people stop trusting the number. The partial feed index carries the predicate too, or every read falls back to a scan. Dismissal is per ROW, so one person clearing a broadcast leaves everybody else's copy alone. `markUnread` is the mirror of `markRead` and exists for the same reason an email client has it: having read something and having dealt with it are different, and un-reading is the only way to say "come back to this". **The bell links to `/notifications#<id>` rather than handling the click itself** — the dropdown truncates, so a click that only marked it read left the text somebody was reaching for still cut off; the page opens that one and scrolls to it.

    16. **NOTIF-24 (2026-10-14): email goes out through TWO providers, and the CATEGORY decides which — SES went live tonight.** `EmailProviderRouter` is the one place that picks (CUR-12 applied to email; `EmailDispatchService` has a single send call and nothing else anywhere names a provider). **CREDENTIAL → Resend, always; everything else → SES when it is live.** Credential mail is the one category with no fallback channel by construction (NOTIF-9), so it gets a pipe of its own; it also runs at one or two a day, comfortably inside Resend's free 100/day, while the bulk moves to SES where volume costs $0.10/1,000 instead of $90/month at Scale. The arrangement exercises BOTH paths daily, which is the point — a failover that only runs during an incident is one nobody knows is broken. **Failover is symmetric and classified by the adapter** (CUR-14): a TRANSPORT failure fails over, a MESSAGE failure does not, because a rejected address is a verdict the second provider will share and re-sending doubles the bounce across both reputations. `classifySesFailure`'s `/not verified/i` → TRANSPORT is load-bearing and was written for the sandbox: it also covers an unverified FROM identity, so a half-finished SES setup degrades to Resend rather than losing mail. **Do not "simplify" that regex.** CUR-15 holds too — a stubbed Resend (empty `RESEND_API_KEY`) may never answer for a live SES, or a message comes back "sent" with a null provider id and nobody receives it. **SES IS INERT BY ABSENCE**: remove the three `AWS_SES_*` variables and everything routes to Resend with no code change, which is how it shipped dark for weeks. **Reason about which provider is live from the ENV on the droplet, never from this file** — the same rule the Delhivery write posture has, for the same reason. DNS, the records, the two silent failures this setup actually hit, and the measured Gmail headers are in `docs/email-dns.md`. Measured volume when SES was switched on: 286 emails sent all-time, 120 in 30 days, busiest day 70 — so **the 100/day Resend cap was the live constraint, not the 3,000/month one**. The thing that will actually drive volume is customer-email CAPTURE, running at ~4% (117 of 403 rows are SKIPPED `customer.*` with no address, NOTIF-8); at full capture one order generates ~5 customer emails.

    17. **NOTIF-25 (2026-10-14): a failover that WORKS is still news, and it was silent.** The router falls back to the other provider on a TRANSPORT failure, the message goes out, and nothing looks broken — which is the design working and also how the estate can run for weeks on its RESERVE provider with a `warn` line as the only trace. `EmailDispatchService.announceFailover` raises a HIGH INTEGRATION issue, and each direction hides something different: **Resend → SES** is almost always the free tier's 100/day, which matters because credential mail is the one category pinned to Resend (NOTIF-24) precisely for having no in-app copy (NOTIF-9) — delivery survives, and knowing is what lets somebody upgrade before the day SES is unavailable too; **SES → Resend** reads milder and is worse, because SES carries the bulk and a sustained outage pushes all of it onto a 100/day cap it will exhaust in hours, after which credential mail has nowhere left to go. **HIGH and NEVER CRITICAL** — NOTIF-16 makes CRITICAL additionally EMAIL, so a CRITICAL here would ask the degraded system to report on itself through the provider that just failed; HIGH is in-app only and reaches the same people. **One issue per DIRECTION, not per message** (TRK-11's rule: a spent quota fails over everything that hour, and a row each is a list people stop reading). AWAITED in a try/catch rather than fired and forgotten — a failover is rare so the latency is nil, and it avoids becoming a tenth fire-and-forget DB writer needing its own drain hook (NOTIF-19); it can never throw, because the message has already gone and an alerting layer that fails the operation it describes is worse than none. **The classification underneath is what makes credential failover possible at all, and it was untested**: `classifyResendFailure` reads `daily_quota_exceeded` as TRANSPORT, which is the only reason a password reset survives the cap. That Set reads exactly like a list somebody could tidy, and dropping that entry gives the worst shape this codebase knows — a reset never sent, on the busiest day, with no second channel and nothing raised, because MESSAGE-kind failures deliberately do not fail over (CUR-13). `resend.service.spec.ts` now pins it.

    15. **NOTIF-23 (2026-09-20, owner): a message with an inbox behind it is not also emailed, and `RETIRED_EMAIL_TEMPLATES` is the ONE list that says so.** All three identities have an inbox now (staff and seller since NOTIF-9..21, a reseller store since 2026-09-19), so twenty-five templates were arriving twice. **The two RETURN notices (`shipment.rto_initiated.seller`, `seller.order_rto_received`) were added on the volume figures**: at ~30,000 orders a month and a 15–25% return rate they are ~9,000 emails a month between them, about nine tenths of what was left. The map is `template code → the in-app topic that now carries it`, in `common/notifications/retired-email-templates.ts`. **A MAP, not a set, and that is the whole safety argument**: dropping an email leg only MOVES a message if the other channel exists — without one it DELETES it, silently, because nothing fails when nobody is told. `retired-email-templates.spec.ts` asserts every value is a topic the catalogue actually serves, so a code added with no inbox route fails the build. The topic is the code minus `.email` (NOTIF-14) except for the three ticket emails, whose topics are named for the EVENT (`ticket.opened_for_you|reply|resolved`); the spec names those three as the only exceptions. **Gated in TWO places, both before anything is written**: `NotificationLedgerService.enqueue` returns `kind: 'RETIRED'` and writes NO row (a row for a send that cannot happen sits QUEUED forever and NOTIF-22's watchdog would re-queue it and then raise `email-undelivered` about a message nobody meant to send), and `EmailQueue.enqueue` is the backstop every email in the estate passes through. **The backstop withholds only from a recipient who HAS an inbox** — `recipient.id === null` is an ad-hoc address, a shared mailbox an operator pointed a setting at, and there is no inbox behind it; the live case is `marketing.lead_notification_email`. **Senders are left composing their email exactly as they did**, so putting one back is deleting a line from the map, not restoring a deleted code path. **Still ON**: `seller.order_cancelled`, the consignment emails, `topup_accepted`/`topup_rejected`, `account_suspended`/`account_reapproved`, `seller.goods_receipt_completed`, `seller.stock_adjustment_executed`, `store.terms_published`, the two store ticket copies and `store.order_changed_by_admin`. **Deliberately NOT retired**, each for a reason about the RECIPIENT rather than the message: every CREDENTIAL template for all three identities (NOTIF-9 — an invitation has no account to be read from, a password reset you must sign in to read is useless), every `customer.*` (no customer login in Phase-1A), `marketing.invite_lead_ack.email` (the lead is a stranger), and the CRITICAL `system_issue.*` email (NOTIF-16 emails only CRITICAL precisely so it reaches somebody NOT looking at the admin app). **Retiring a template that had no in-app leg means ADDING one first** — six did (`staff.invite_lead`, `seller.order_needs_attention`, `seller.stock_low_alert`, `seller.goods_receipt_discrepancy`, `seller.invoice.delivered`, `seller.topup_submitted`), each addressed by the PERMISSION that opens the page it is about, each with a catalogue entry so it can be silenced, and each dispatched POST-COMMIT where its email sat inside a transaction (INV-5).

    14. **NOTIF-22 (2026-09-12): an email row that never went out cannot sit QUEUED silently.** Store-then-send leaves only the job able to move a row out of QUEUED, so a job that dies early leaves it QUEUED forever. On production the three CRITICAL `system_issue.money` emails of 7 Sep did exactly that for five days: the template did not exist, the render threw before the row was touched, and the exhausted job raised only a MEDIUM issue, which notifies nobody — while the in-app copies arrived and made everything look fine. **A render failure is now written onto the row** (`TEMPLATE_NOT_FOUND` / `RENDER_FAILED`, guarded on QUEUED, status unchanged so BullMQ keeps its retries). **`EmailDeliveryWatchdogService`** (own `email-watchdog` queue, every 15 min, SCALE-1) looks at QUEUED email rows untouched for 30 min with no live job — a quiet-hours delay is a live job and is left alone — and re-queues each ONCE through the `existingNotificationLogId` path, claimed by a guarded `attempt_number` 1→2 before enqueueing. A row still unsent after that, older than 24h (a late password reset or a stale "Critical" alert is worse than none), or with no address is marked FAILED with the reason and last error, and reported once as a HIGH `email-undelivered` issue — in-app, never by email (the channel that is failing), never auto-cleared. **A new store-then-send email path needs nothing extra.** The re-send renders in the default language (the row does not store the locale).

    12. **NOTIF-20 (2026-09-05): an issue nobody was told about can be told about later, and the retry is safe BY CONSTRUCTION.** `raise()` only announces a NEW issue (NOTIF-16), so everything already open the day notifying shipped is otherwise silent forever — and there is a standing hole of the same shape, because `notify()` swallows its own failures on purpose and a failed dispatch leaves an issue open with nothing anywhere to say it was never announced. `SystemIssueNotifier.announceUnnotified()` finds them: open, HIGH-or-CRITICAL, with no `notification_logs` row carrying their `system_issue:<id>` event id. **Idempotence is a property of the dedup key, not of the query being right** — a re-run re-sends the identical event id and the NOTIF-2 partial unique refuses it — which is what makes it safe to put behind a button rather than a one-off script. OPERATOR-TRIGGERED (`POST /admin/system-issues/announce-unnotified`, `system.settings.manage`, audited MEDIUM: it is a catch-up on notifications that should already have gone, not a new thing being said), surfaced on `/system-issues` as "Notify unannounced". Sequential rather than parallel on purpose — this is a handful of rows by definition, and if it were ever many the right response is to ask why that many problems are open.

    11. **NOTIF-19 (2026-09-05): the THIRD drain hook, and the rule that predicted it.** `SystemIssueNotifier` writes `notification_logs` from paths that are themselves fire-and-forget — a sweep, a listener, a catch block — so those writes outlive whoever triggered them. In production that is correct. In the e2e harness it deadlocks the reset: the INSERT holds a `RowShareLock` on `orders` while the TRUNCATE wants an `AccessExclusiveLock`, and Postgres kills one with a **40P01 that names neither the test nor the cause**. It arrived exactly that way — green locally, red on one CI shard out of four, inside `order-shipment-wiring` which has nothing to do with notifications. The fix is the one CLAUDE.md already prescribed for "ANY future post-commit fire-and-forget side-effect that writes via async DB calls": track in-flight Promises in a Set, expose `drainInFlight()`, await it in teardown. `resetAuthState` now drains THREE (`NotificationListener`, the AWB listener, `SystemIssueNotifier`) and a new one belongs in the same list **in the same commit that adds the writer** — the rule was written down before this and would have prevented it had it been applied when the notifier was added rather than after CI found it.

    10. **NOTIF-18 (2026-09-05): every audience the API can resolve is one a person can pick.** The broadcast screen shipped offering five of ten selectors; the other five were not broken, they were unreachable — the same class of gap as an endpoint with no caller, and it looks identical to never having been built. All ten are offered now, each declaring the FIELDS its selector needs (a role or permission at a seller needs the company AND the thing), and preview is blocked until every named field is filled — a selector missing half of itself resolves to nobody, and "0 people" is a confusing way to learn a box was left empty. Pinned by `apps/admin/src/tests/broadcast-audiences.test.ts`. **When adding a selector kind, add its option in the same change** — the test fails until you do.

    **The seller's notification settings are ONE page at `/notifications/settings` holding TWO grains (merged 2026-09-08).** They were two screens — a person's own per-topic silences, and the COMPANY's per-category email preferences (M1-era `seller_notification_preferences`) — reached from two Settings tiles both called notifications, distinguishable only by reading the descriptions. That is how somebody changes the wrong one and believes they changed the other.

    **The SCREENS merged; the two data models did NOT, and must not.** The question this doc asked before merging — what does a per-company mute mean for a person who did not set it? — is answered in `SellerNotificationPreferenceResolver`: both grains can only ever REMOVE a delivery, never add one, and they compose by intersection. The company decides whether a category leaves the building at all; a person decides what reaches their own inbox. One table holding both would have to answer "whose choice was this?" per row, and cannot. So: one page, two sections, each stating whose decision it is.

    **The url is the UNGATED one, and that is load-bearing.** `/settings/notifications` sat behind `notifications.manage` — correct for an administrative act — but a person's own inbox is self-service and must never be behind a grantable permission (NOTIF-11): no existing role holds that key, so most of the estate would have been bounced off their own settings. The merged page is ungated and the COMPANY half is gated cosmetically inside it (FE-2 — the API refuses the PATCH regardless). `/settings/notifications` survives as a redirect for old bookmarks, its `page-access.ts` entry deliberately removed so an old link lands somebody on their own settings rather than bouncing them to the dashboard; it is listed in `pages-are-reachable.test.ts`'s `EXPECTED_UNLINKED` with that reason.
