# Console renames and user-facing copy (CON-1, CON-2)

**CON-1 (2026-10-13): the three consoles were RENAMED, and the OLD names SERVE rather than redirect.** `app.` → `client.`, `reseller.` → `member.`, `portal.` → `associate.` (all `.global`; a new host never gets a `.online` name — but `.online` itself is NOT retired, it is still serving six live hosts, see CON-2). **A redirect was not an option and that is the whole design**: a `__Host-` cookie is bound to the exact origin that set it, so a browser redirected from `app.` to `client.` arrives carrying NO session — every signed-in seller logged out at the cutover, every bookmark landing on a login screen. So both names serve the same app, on one Caddy block each, and nothing is lost in between. **Everything the system GENERATES points at the new name** — invitations, password resets, email verification, the impersonation handoff, the marketing sign-in buttons — through `SELLER_APP_URL` / `RESELLER_APP_URL` / `ASSOCIATE_APP_URL`, all three now stated explicitly in production's `.env` rather than left to a default. `EnvService.corsOrigins` returns the new names from env PLUS the hard-coded `LEGACY_CONSOLE_ORIGINS`; that list is hard-coded on purpose (a fixed, finite, CLOSING set is not a knob somebody can point anywhere) and **only ever shrinks** — when a name goes quiet it becomes a `redir` in Caddy and its entry comes out of there. **This is a transition, not an end state**: three extra live origins is a cost, the runbook's step 5 is how it ends, and `docs/console-rename-runbook.md` holds the log-watching command. **A dated record keeps the name that was true on its date** — `docs/infrastructure.md`'s RS-12 and ASSOC-1 go-live sections, deploy.sh's 2026-09-27 incident note and the redaction corpus's "Production shapes, 2026-09-30" were deliberately NOT rewritten, because a rename that edits history makes the history useless for the next person debugging from it.

**CON-2 (2026-10-14): the WORDS followed the hostnames — "seller" reads as "client", "reseller store" as "member store" — and NOTHING under the surface moved.** CON-1 renamed the three origins and left the copy inside them saying "seller portal" and "Reseller stores", so the product disagreed with its own address bar. This is the other half. **The rename is USER-FACING TEXT ONLY, and the line is worth stating exactly, because the deeper version is a different project with a different risk:** labels, headings, buttons, placeholders, empty states, notice prose, column headers, nav items, page titles, email and notification subjects and bodies, and the marketing site. **UNCHANGED, deliberately:** every identifier (`sellerId`, `SellerJwtGuard`, `ResellerStoreService`), every route (`/seller/*`, `/store/*`, `/admin/sellers/*`), the cookies (`__Host-sellerRefresh`), the JWT audiences, `identityKind: 'seller' | 'store'`, permission and system-setting KEYS (`stores.manage`, `reseller.orders_enabled`), notification TEMPLATE CODES and TOPIC KEYS (`seller.order_dispatched.email`), enum values (`ActorType.SELLER`, `StoreKind.RESELLER`), the database, and URL fragments like `/#resellers`. Two of those would have been outages rather than renames: **the cookie rename signs every user out** — precisely what CON-1 served the old hostnames to avoid — and **a `/seller/*` → `/client/*` route rename breaks every seller API key and webhook consumer** silently, from the integration's side, with no error we would ever see. The database half (`sellers`, `seller_id` on ~100 tables, the enum values) is a quarter-scale migration and was not attempted.

**So the UI word and the code word differ ON PURPOSE, and that is the thing to know before reading this codebase**: a screen that says "Client" is served by `SellerJwtGuard` off `sellers.id` through `/seller/orders`, and a screen that says "Member store" is `seller_stores` with `kind = RESELLER`. **Code COMMENTS were left alone for the same reason** — they describe symbols that still say seller/reseller, so rewriting them would have made ~5,000 comments disagree with the code beside them. The ONE exception: a comment that QUOTES a string that changed is updated, because a quotation that no longer matches what renders is simply wrong.

**HOW TO FIND USER-FACING COPY, because two scans missed in opposite directions and both missed SILENTLY.** This rename was driven twice off a scan anchored on the FIELD — `/^\s*(label|description|title|note|reason|message): '(.*)'$/` — and that shape is blind to three forms that are everywhere in this codebase: a **ternary** (`detail: cond ? '…seller…' : '…'` — the literal does not follow the field), a **`const` holding the word** (`const asker = store ? 'reseller store' : 'seller'`, interpolated into both a title and a detail), and a **multi-line continuation** (a description whose string begins on the next line, which is how every long permission description is written). Nine persisted-prose sites and twenty-seven permission descriptions were missed that way, and two of the misses were WORSE than an omission because they left one feature speaking both vocabularies: `early-reservation-decision` wrote "Seller asked for more call attempts" while its own sibling `review-expiry-sweep` wrote "Client…", and the RS-7 dispute ledger note said "reseller store" beside a UI direction label that already said "member store". **Anchor on the WORD and filter by what reaches a persisted column or a rendered string — never on the field name.** The second scan, anchored on the word, found all of it in one pass.

**A SCRIPTED `seller` → `client` REPLACE MANGLES A BARE "reseller" INTO "reclient", and it happened TWICE.** `'reseller'.replace('seller','client')` is `'reclient'`; it shipped into three permission and topic labels in one pass and one more in the next, each time because the generic replacement ran LAST without a bare "reseller" having been mapped first. A rename of these two words must neutralise "reseller" BEFORE touching "seller" — map every `reseller…` form to its target first, and then assert the output contains no `reclient` — because the result is a real word-shaped string that typechecks, lints, formats and renders. `grep -rn reclient` is the check, and it belongs in any future pass.

**The CHANNEL store is a "SHOP" (owner, 2026-10-14), and the two words now carry the two kinds.** `seller_stores` holds both: `kind = CHANNEL` is one of a client's own shopfronts (their products, stock, wallet and couriers are shared across all of them), and `kind = RESELLER` is another business selling that client's stock under its own name. The first pass renamed them "Client stores" and "Member stores", which left the whole distinction resting on one word in two adjacent nav items — so CHANNEL became **"shop"** and only RESELLER keeps the word "store". **The line is drawn by what a surface can SEE, not by the word it uses**: `SellerStoreService` is CHANNEL-only by construction (RS-1 — every query filters `kind: CHANNEL`), so its screen, its nav item and its own refusals say "shop"; an ORDER-level label says "store" and stays, because `orders.store_id` may point at either kind and "Store" is the only word true of both. **A new surface that names a store asks which kinds it can receive before it picks a word.** The `STORE_NOT_FOUND` code and every other identifier are untouched, as everywhere else in CON-2.

**The API's own sentences are user-facing too, and that is FE-2, not a nicety.** The UI shows a server refusal as `[CODE] message` verbatim and is forbidden from pre-empting it — so an API message is product copy by construction, and 107 of them named a seller or reseller while the console around them said client. They are renamed; the `code:` beside each one is not, because the frontends switch on it. **Log lines are deliberately NOT renamed** (developer-facing, and they print the symbols that still say seller), and nor are Swagger examples.

**"member" was already taken, and the two-word form is what keeps it unambiguous.** `member`/`members` means A PERSON ON A TEAM in these apps and has for months (admin 66 uses, client 86, store 63 — "Members", "Invite member", "Team member deactivated"). So a reseller store is **always "a member store", never "a member"** — even on a screen that is obviously about stores, and even where the original said a bare "reseller". Where repetition gets clumsy the later mentions are "the store", which was already the right word and is what a store user reads about themselves: **inside the store and sales portals the word "member" never appears about the reader at all.** Shortening it anywhere reintroduces one word meaning a human on one screen and a business on the next.

**The CONSOLE DIRECTORY is one list: `CONSOLES` + `OtherPortals` in `@skydrop/ui/app/sign-in`.** Every console's sign-in screen used to carry ONE hand-written link to ONE other console, written three times in three apps — so the mesh was partial by accident rather than by decision (client offered member, member offered client, associate offered member), and **an associate who landed on client could reach member and from there only client again, never their own portal.** `OtherPortals self={...}` renders every console EXCEPT the caller's, so a console cannot be left off somebody else's page by omission, and the next rename — or a fourth console — is one edit instead of six scattered literals. It is on `/login`, `/password-reset` and `/sign-up` in all three. **`/password-reset` matters more than `/login`**, because the API answers a reset request identically whether or not the email has an account there (anti-enumeration): somebody in the wrong console is told a link is on its way and then gets nothing — a dead end that READS AS SUCCESS and teaches them to wait. **ADMIN is deliberately absent from the list**: nobody arrives at a customer portal looking for Skydrop's operations console, and advertising its address on three public pages is noise for every real visitor. The links are CONSTANTS, not env — our own fixed, finite set of public hostnames, the same argument CON-1 made for `LEGACY_CONSOLE_ORIGINS`; what the API GENERATES still comes from env, because those addresses are per-environment and land in somebody's inbox. Consequence, stated: in local dev these links leave localhost for production, exactly as the literals they replaced did.

**`/sign-up` exists in all three consoles and carries NO FORM, on purpose.** Skydrop is invite-only: a client is invited by Skydrop (the one public endpoint is marketing's `/api/public/invite-leads`), a store by the client whose stock it sells, a sales person by their store. So each page leads with the one real next step and says plainly who invites you — **a form here would be a dead end dressed as a door.** It exists because `/sign-up` is what a person types, and because each login page says "use the credentials from your invitation" to people who have none; without it that question ended at a 404. The client page offers the real invite request; the store page also offers it, for the business that wanted to ship its own stock and typed the wrong address.

**`storeConsoleUrl` (`common/auth/store-console-url.ts`) is the ONE rule for which console a store user's link points at, and five call sites had re-decided it wrong.** ASSOC-1's rule — only-`associate` roles ⇒ the associate origin, anybody wider ⇒ the store origin — was written for invitations and lived in `store-team.service.ts` as `invitationAppUrl`. A link audit found the reseller console hardcoded in `store-auth`'s password-reset, password-changed and email-verification links, in `ticket-notifier`'s `ticket_url`, and in `store-notification-sender`'s shared `links` block. **Two of those are CREDENTIAL mail**, which by construction has no in-app copy (NOTIF-9) — so a sales person had exactly one channel and it pointed at an origin where `__Host-storeRefresh` cannot follow them and almost every page refuses them. The rule moved into a dependency-free module both modules import (the R3 extraction rather than a `forwardRef`), and is NAMED for the question it answers: `invitationAppUrl` was accurate when invitations were the only link, and a name that narrow is how five other sites came to decide it for themselves. **Empty roles fall to the WIDE console** — no live roles is "unknown", not "narrow". `apps/associate` was also MISSING `/auth/reset-password` and `/auth/verify-email` entirely, which is why nobody had noticed: the API never sent anybody there. **A new place that builds a link for a store user calls `storeConsoleUrl`, and a new store-user-facing page exists in BOTH store consoles or the link 404s.**

**`.online` IS STILL SERVING — six live hosts — and this file said otherwise.** Measured 2026-10-14: `skydrop.online`, `app.`, `reseller.`, `admin.`, `api.` and `track.skydrop.online` all answer 200 and SERVE (no redirect); only `portal.skydrop.online` was never created. CON-1's text above claimed `.online` "is retired", and `docs/infrastructure.md` says it "is retired once `.global` serves" — neither is true yet, and nothing is broken by that (the consoles reach the API through their own same-origin proxy, FE-3, so the `.online` origins' absence from `LEGACY_CONSOLE_ORIGINS` costs nothing). **Two consequences that do bite**: the runbook's step-5 traffic grep matches `(app|reseller|portal)\.skydrop\.global` and therefore CANNOT SEE `.online` traffic, so "this name is quiet" judged from it is incomplete; and the estate is ~17 live hostnames, not 11. **Retiring `.online` for real, or amending both documents, is the owner's call — but the documents and reality must not keep disagreeing**, because the next person debugging will trust the wrong one.
