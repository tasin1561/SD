**Key invariants added by the R-phases:**

1. **SET-1 (R0): `SettingsResolverService` is the ONLY resolver AND the only writer of `seller_setting_overrides`.** Resolution is `sellerOverride ?? systemDefault`; a key is overridable only when `system_settings.sellerOverridable` is true, and INT/DECIMAL overrides are clamped to `overrideMin*/overrideMax*` AT WRITE TIME (not just in the UI). New seller-configurable behaviour goes through this mechanism — do NOT add another nullable column on `sellers` (the two legacy ones, `callMaxAttemptsBeforeNdrOverride` / `reservationTtlHoursOverride`, are the grandfathered exceptions).

3. **CACC-1 (R1): a shipment records WHICH courier account carried it.** `Shipment.courierAccountId` + `SellerCourierAccountLink.distributionWeight` drive weighted per-seller routing. Never infer the account from `courierCode` after the fact.

4. **WAL-1 (R2): `WalletService.applyEntry` stays the sole wallet writer, and every new `WalletEntryDirection` MUST be registered in its `CREDIT_DIRECTIONS` set.** Forgetting registration silently takes money FROM the seller instead of giving it. `apps/seller`'s ledger view mirrors the same set — both sides must be updated together (the R7 `SCRAP_REFUND` addition caught this twice).

5. **WMS-8b (R6/R6b): RTO can be RECEIVED at any ACTIVE warehouse, and a cross-warehouse RESTOCK credits the RECEIVING warehouse — never the origin bin.** `stock_batches` is warehouse-scoped, so crediting the origin bin for goods standing in another building would be silent corruption. R6 refused outright; **R6b** resolves a real target instead via `RtoRestockTargetService`: find-or-create a CHILD batch at the receiving warehouse (deterministic `<parent>-RTO-<warehouse>` code — that is what makes it find-or-create rather than a unique-collision) inheriting `expiresAt`/`manufacturedAt` (FEFO stays correct), `unitCostInr` (margin stays honest), `receivingNoteId` (the batch → goods receipt → inbound-freight chain still resolves for a returned unit that later sells) and `parentBatchId` (explicit lineage), plus an `RTO_HOLD`/`STORAGE` bin there. It still refuses when the warehouse has no bin able to hold returns (`RTO_RESTOCK_NO_TARGET_BIN` — a missing setup step, not something to guess). **Amended by WMS-8e (2026-09-14):** the child batch is made at RECEIVE for a line booked into the returns hold, and a RESTOCK now lands in a sellable bin at the receiving warehouse (FLOOR, which self-heals), so `RTO_RESTOCK_NO_TARGET_BIN` no longer arises. Cross-warehouse write-off is always allowed (no movement). The R4 unit ledger follows the resolved target, never the original bin/batch.

6. **TKT-1 (R7): `TicketService` is the sole writer of `tickets` / `ticket_events`; `ticket_events` is APPEND-ONLY.** One state machine covers both auto-raised scrap/damage (opened in the SAME tx as the RTO inspection) and seller-raised parcel issues. Refund resolution credits the wallet via `SCRAP_REFUND` inside the transition tx. `open` is idempotent per `(shipmentItemId, ticketType)`. **AMENDED 2026-09-13: every ticket has a NUMBER, an auto-raised ticket always opens with OUR message, and the opening bubble follows who opened it.** `tickets.ticket_number` is `TK-YYYY-NNNNNN` (UNIQUE, NOT NULL), allocated by `allocateTicketNumber` (`ticket/services/ticket-numbering.ts`) from the per-year `ticket_number_seq_<YYYY>` under `AdvisoryLock.TICKET_NUMBER`, INSIDE the transaction that inserts the ticket — the ORD-8 pattern; `open`/`openOrFind` run in the caller's tx (the RTO inspection's) or open one of their own, and the idempotent path returns the existing ticket before anything is allocated, so a retried inspection never burns a second number. No month segment: the serial is per year, so a month adds nothing to uniqueness, and this is the identifier most often read down a phone. URLs stay on the uuid; both ticket lists search by number (and subject / order / parcel / waybill), and each app's header search resolves a `TK-…` term to its ticket. Backfilled oldest-first by `20260913000200_ticket_numbers`. The RTO inspection opens a SCRAP_DAMAGE ticket with `scrapTicketOpeningMessage()` (`warehouse-rto/services/rto-scrap-ticket-message.ts`, pure): the ticket number, product + SKU, the line's quantity, what was found (arrived damaged / missing from the returned parcel), order · parcel · waybill, when and at which warehouse it came back (receiving, else origin), what we are doing with the unit, the inspector's notes QUOTED inside it, and what happens next — never a refund figure. It used to open with the inspector's notes alone, so a ticket inspected without notes read "Nothing said yet." to the seller (production's SD-TEST-524086; filled by the one-off `20260913000300_scrap_ticket_opening_messages`, empty descriptions only). A re-inspection that CHANGES the finding on an open ticket adds our note via `addNote` in the inspection tx (a correction to GOOD included); the opening message is never edited. `TicketView.openedBy` (`STAFF`/`SELLER`/`SYSTEM`, from the opening event's actor, else the `opened_by_*` columns) decides which side both conversations draw the opening bubble on — it was drawn as the seller's ("You") on every ticket; only a seller's opening message carries TKT-2 relay state. An empty open thread still shows the reply box.

6b. **TKT-3 (2026-09-13): a short count opens a ticket, and every ticket event tells the OTHER side.** The owner: "for decrease shouldn't we create a ticket with all the details like we are doing for damaged or missing RTO products?" — "yes do it". **(a) `RECEIPT_SHORTFALL`.** When `GoodsReceiptService` completes a receipt with any line SHORT (`expected − received − damaged > 0`; `received_qty` counts GOOD units, so a damaged unit is not also a missing one) or any `damaged_qty > 0`, `ReceiptShortfallTicketService.afterCompletion` opens ONE ticket against the seller, keyed on `tickets.goods_receipt_id` (`@@unique([goodsReceiptId, ticketType])` — the open-idempotency key, as `shipmentItemId` is for scrap), actor SYSTEM. It runs AFTER the count commits and NEVER throws (visible-vs-silent: the count and stock are the fact, the ticket its reflection; a failure audits HIGH `inventory.receipt_shortfall.not_raised`, and a completed short receipt with no ticket is exactly what the backfill's dry run lists). **CNS-3 is untouched — nothing blocks, holds stock, or moves money**; staff may settle through the existing refund path. The opening message is ours (`receiptShortfallOpeningMessage`, pure, `inventory-receipt/services/receipt-shortfall-ticket-message.ts`): ticket number, consignment + receipt, warehouse and count date (warehouse zone), one line per affected SKU (`declared|sent N · counted N · damaged N · short N`), and WHICH LEG: the first count anybody made (the Dhaka intake, a DIRECT_IN's Indian warehouse, or India after a Dhaka stop that forwarded UNOPENED) is the seller's declaration against us — we ask them to confirm or dispute; the India leg of a VIA_BD consignment after a COUNTED Dhaka stop (`dispatchedAt` set) is a loss in OUR hands — we look into it and may settle on the ticket; damaged units are taken up with the forwarder. Never a refund figure. **A surplus is NEVER a ticket**: an in-app INFORMATIONAL notice (`inventory.receipt_surplus`, to `SELLER_PERMISSION inbound.view`, eventId `receipt_surplus:<receiptId>`, gated by the company's STOCK_ALERTS preference). A forwarded-without-count receipt is skipped (no number to be short of). Catch-up: `POST /admin/goods-receipts/shortfall-tickets/backfill` (`inventory.goods_receipts.manage`, body `{ dryRun?: boolean }`, DRY RUN by default with the exact words it would write, audited LOW/HIGH, idempotent) — the ticket for production's GR-2026-08-0004 is raised by running it, deliberately NOT by a migration (opening a ticket messages the seller). **(b) `TicketNotifier`.** `TicketService` hands every event it writes (open, note, transition) to `TicketNotifier.afterEvent`, fire-and-forget, NEVER throwing, drained by `resetAuthState` (NOTIF-19). The pure `planTicketNotification` decides: OUR words (STAFF/SYSTEM) go to the seller — opened for you, a reply (a note, or a move carrying one), and every SETTLED outcome with its refund amount; the SELLER's words (SELLER/API) go to staff — opened, replied; a move with nothing said tells nobody; nobody hears about their own act. Seller: in-app to `SELLER_PERMISSION tickets.view` (eventId `ticket:<eventId>:inapp`) and the company email through the ledger (`ticket:<eventId>`, templates `seller.ticket_{opened,reply,resolved}.email`, seeded — deploy reseeds when seed.ts changes), both gated by `SellerNotificationPreferenceResolver` under `sellerCategoryFor(ticketType)` (F2: RECEIPT_SHORTFALL → STOCK_ALERTS, the parcel types → SHIPMENT_UPDATES); OPERATIONAL, never CREDENTIAL. Staff: in-app to `STAFF_PERMISSION tickets.view` (`ticket:<eventId>:staff`). **A caller may hand over an event from INSIDE its own transaction** (the RTO inspection opens its scrap ticket in its tx): the notifier reads the event back on a short schedule and sends nothing for one that never becomes visible (a rollback). The five topics are in the catalogue (NOTIF-17) and pinned by `notification-topic-catalog.service.spec.ts`, whose staff direction now allows named non-issue senders. **A new place that writes a ticket event goes through `TicketService`, or nobody is told.**

7. **RES-2 (R5): an at-placement hold is opt-in, best-effort, and its unbook path is explicit.** `bookingStage` distinguishes AT_PLACEMENT from AT_CONFIRMATION (orthogonal to phase-1/phase-2). `reserveAtPlacement` NEVER throws — order creation must not fail because a hold could not be taken. At the NDR cap, `handleNdrCap` runs BEFORE the REJECTED_NDR transition (durable side-effect first) and either auto-releases with `NDR_CAP_REACHED` or raises an `early_reservation_reviews` row for the seller.

8. **UNIT-1 (R4): `stock_units` is a SIDECAR; `stock_levels.qtyOnHand` stays authoritative for BOTH modes.** `StockUnitService` is the sole writer of `stock_units` / `stock_unit_events` (append-only) and WRAPS the aggregate layer inside the caller's tx — never replaces `StockMutationService` (INV-1 intact). Strict mode adds enforcement, not a second source of truth; where the two disagree the discrepancy report SURFACES it rather than auto-correcting (auto-correction destroys the evidence).

9. **UNIT-2 (R4): scan gates are per-line at pick, set-equality at pack, parcel-grained after that.** Pick requires exactly `quantity` serials and commits the scan + the bin/batch hint in ONE tx. Pack requires the scanned SET to equal the parcel's PICKED units (a count check would pass a swap) and runs BEFORE the pack stamp. Dispatch handoff / RTO receive / RTO disposition move units parcel-grained, BEST-EFFORT and guarded on `fromStatus` — the physical event already happened, so a unit-ledger failure must never undo it. Mode resolution FAILS OPEN to NORMAL so a settings outage can't stop the floor.

12. **SETL-1 (R2c): every rupee the courier pays US is recorded and matched to the orders it covers.** `courier_settlements` is UNIQUE on `(courierAccountId, reference)` — the courier's own payout reference is the gate against recording the same bank credit twice and inflating what we believe we've been paid. Each line snapshots the order's expected COD, so `settled − expected` is a permanent per-order short-payment record. A payout whose `allocatedInr` ≠ `amountInr` audits HIGH. The ledger NEVER writes a wallet entry: a courier short-payment is a dispute with the courier, not a clawback from a seller who was paid in good faith. Append-mostly — correct a mistake with an adjusting settlement, never by editing a past one. Ageing in the reconciliation report uses `orders.updatedAt` as the delivered-at proxy (the exact scan is in the `tracking_events` hypertable and joining it would turn a finance report into a scan); if that precision ever matters, add a `delivered_at` column rather than the join.

**R5b (landed):** `AWAITING_SELLER_DECISION` is a 29th OrderStatus — a PAUSE between the call cap and rejection for MANUAL_REVIEW sellers, with edges out to `PENDING_CONFIRMATION` (keep trying; CC-6 re-enqueues) and `REJECTED_NDR` (release / TTL). CC-2 stays intact: the mapping owns the at-cap transition and takes an `atCapPolicy` the caller resolves from settings. `handleNdrCap` raises a review even with ZERO holds (the question is about calling, not only stock). An hourly TTL sweep (72h default, seller-overridable) releases holds and rejects an unanswered review, so the status can never become a stock-holding black hole. The decision endpoint lives in the LEAF `early-reservation-decision` module because `order` already imports `early-reservation` — composing both there is the R3 rule's answer when the transition boundary itself is not extractable.

**R2c (landed):** the float is now BOTH mitigated and measurable. (a) The default `wallet.accrual_timing_tier` is `T_PLUS_N` with `accrual_delay_days` 7, so a seller is credited after the courier has settled rather than at DELIVERED — a data migration was required because `seedSystemSettings()` is create-only on value columns, so changing the seed alone would not have touched the deployed DB. INSTANT remains a per-seller opt-in (and the shape a paid instant-credit tier would take). (b) **SETL-1**: `courier_settlements` (UNIQUE on `(courierAccountId, reference)` — the courier's own payout ref is the double-count gate) + `courier_settlement_lines` (UNIQUE per `(settlement, order)`; `expectedInr` snapshotted from the order's COD so `settled − expected` stays a permanent short-payment record). `CourierSettlementService.reconciliation()` totals the outstanding float, ages delivered-but-unsettled orders, and lists short-paid ones. It NEVER touches a wallet: a courier short-payment is a dispute with the courier, not a clawback from a seller paid in good faith. An unexplained payout (amount ≠ allocated) audits HIGH.

**Deferred, awaiting a founder decision (documented in code where they bite):**
- **INSTANT_PRIORITY as a paid tier** — the mechanism exists (per-seller INSTANT); what is missing is the price and whether enrolment should be gated on a courier account's float staying inside its settlement window. Now answerable, because R2c measures it.
- **Freight on unsold stock** — a consignment's freight is now amortised per unit as units leave (delivered or written off), so stock still sitting in the warehouse legitimately owes nothing yet. What is undecided is whether an ageing PAY_LATER bill on stock that never moves should eventually be called in, and after how long.
